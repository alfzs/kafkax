# Аудит бенчмарков (2026-07-07)

> **Статус: регрессий не найдено; одна открытая рекомендация (CI regression detection) — ждёт решения.**

Аудит методологии измерения производительности: соответствие бенчмарков `producer_bench_test.go` /
`consumer_bench_test.go` статистической строгости, проверка отсутствия регрессии после модернизации
из `5d20a8d`, и покрытие CI автоматическим детектированием регрессий.

## 1. ✅ Проверено — модернизация не регрессировала перф-фикс

Числа benchstat в `docs/performance-audit.md` были измерены **до** того, как в тот же коммит
`5d20a8d` добавили модернизацию (`sync.WaitGroup.Go`, `t.Context()`, `cmp.Or`,
`slices.Collect(maps.Keys(...))`). Вместо того чтобы считать заявленный результат всё ещё
верным, оба бенчмарка были перезапущены на текущем HEAD (`-count=10 -benchmem`):

| Бенчмарк | Заявлено в коммите | HEAD сейчас |
|---|---|---|
| `BenchmarkProcessMessage_WarmPath` | 46.55 ns/op, 0 B/op, 0 allocs/op | ~47-52 ns/op, 0 B/op, 0 allocs/op |
| `BenchmarkSendMessage_WarmPath` | 41.31 ns/op, 0 B/op, 0 allocs/op | ~36-38 ns/op, 0 B/op, 0 allocs/op |

Расхождение в пределах обычного шума между запусками, аллокации по-прежнему нулевые.
Заявление о перформансе в коммите подтверждено эмпирически, а не принято на веру.

## 2. ⚠️ Пробел — нет детектирования регрессий бенчмарков в CI

`Makefile` содержит таргет `benchmark` (`go test -bench=. -benchmem ./...`), но
`.github/workflows/ci.yml` его не вызывает. Сейчас ничто не помешает будущему PR молча
вернуть ту самую allocation-регрессию, которая была исправлена в `5d20a8d`, — CI об этом
не узнает.

Библиотека pushes/pulls на shared GitHub-hosted раннерах, где даже в простое типичен
шум 5-10% между прогонами (см. `references/ci-regression.md` этого скилла). Из-за этого
жёсткий порог (`cob`) рискует ложно фейлить PR на нерелевантном шуме. Более уместные варианты
для проекта такого размера (2 узких бенчмарка):

- **Минимум:** нерегламентированный шаг в CI, который просто прогоняет бенчмарки и
  публикует вывод как job summary/artifact — только видимость, без гейта.
- **Средний вариант:** `benchdiff`-подобное сравнение с base-веткой, публикуемое
  комментарием в PR — сигнал есть, но жёсткого фейла нет.

Решение не применено — выбор инструмента и порога строгости оставлен на усмотрение
пользователя (см. переписку).

## 3. ℹ️ Отмечено, не применено — fieldalignment на `tenantWorker`/`partitionWorker`

`fieldalignment` (`producer.go:26`, `consumer.go:27`) сообщает, что эти структуры можно
переупаковать для уменьшения диапазона pointer bytes, который сканирует GC. Это ровно те
структуры, которые аллоцируются в холодном пути `getOrCreateWorker` (один раз на тенанта/
партицию) — не в горячем пути, который покрывают текущие бенчмарки.

Изменение не внесено: холодный путь создания воркера сейчас не бенчмаркается вообще, поэтому
нет данных, чтобы подтвердить или опровергнуть, что переупаковка вообще заметна. Правило
этого скилла — не заявлять об улучшении, которое не измерено. Прежде чем применять fix,
нужен отдельный `BenchmarkGetOrCreateWorker_ColdPath`.

Остальные находки `fieldalignment` (`Config`, тестовые структуры) — структуры,
аллоцируемые единожды за процесс; переупаковка не даёт измеримого эффекта и не
рассматривалась.

## Что в порядке

- Оба бенчмарка используют `b.Loop()` (Go 1.24+) и `b.ReportAllocs()`.
- Оба атомарны — изолируют ровно один вызов (`getOrCreateWorker` + `inFlight.Add`), без
  постороннего кода в измеряемом теле.
- `benchstat` установлен и доступен (`go install golang.org/x/perf/cmd/benchstat@latest`).
