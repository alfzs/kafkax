# Аудит observability (2026-07-07)

> **Статус: все находки исправлены (2026-07-07, дополнено 2026-07-07).**

Аудит покрытия пяти сигналов observability (логи, метрики, трейсинг, профилирование, RUM)
для `consumer.go`, `producer.go`, `otel.go`, `config.go`.

RUM не применим — kafkax это backend-библиотека, а не user-facing сервис.
Профилирование (pprof) оставлено на усмотрение приложения, использующего библиотеку —
для самой библиотеки это не пробел.

## Трейсинг

### 1. ✅ `span.RecordError()` нигде не вызывается — исправлено

Везде использовался только `span.SetStatus(codes.Error, ...)`:

- `consumer.go:509`
- `producer.go:417, 430, 435, 451, 455`

`SetStatus` помечает span как ошибочный, но не прикрепляет exception-событие
(тип, сообщение, стек). Из-за этого в трейсинге теряется детализация по каждому
сбою.

**Фикс:** рядом с каждым `span.SetStatus(codes.Error, ...)` в `consumer.go` и
`producer.go` добавлен вызов `span.RecordError(err)`.

## Метрики

### 2. ✅ Высококардинальный label `tenant_id` — исправлено

`producer.go:172` — observable gauge `kafkax.producer.queue.depth` использовал
`tenant_id` (UUID) как атрибут. При росте числа тенантов до нескольких тысяч
это прямое нарушение правила "не использовать unbounded-значения как label" —
кардинальность метрики в бэкенде взорвётся. Аналогичный gauge у консьюмера
(`consumer.go:188`) в порядке — там `topic`/`partition` ограничены.

**Фикс:** callback гейджа больше не проставляет `tenant_id` как атрибут —
глубина очередей суммируется по всем тенантам и публикуется одним значением
без per-tenant разбивки.

### 3. ✅ Survivorship bias в `messageLatency` — исправлено

`producer.go:441` — гистограмма latency писалась только на success-пути в
`produce()`. Ошибки продюсирования, ошибки доставки, таймауты и отмену
контекста метрика не видела вовсе. В результате p99 мог выглядеть здоровым,
даже когда доля неудачных отправок растёт — неудачные запросы просто выпадали
из распределения.

**Фикс:** `produce()` переведён на именованный возврат `err`, запись в
`messageLatency` вынесена в `defer` и выполняется для любого исхода функции,
с атрибутом `status=success|error` для различения успешных и неуспешных
попыток в гистограмме.

## Логи + трейсы (корреляция)

### 4. ✅ `trace_id` прикреплён к логам только в продюсере — исправлено

`producer.go:201-205` вручную доставал `trace_id` из span context и добавлял
его в логгер — обходное решение вместо `otelslog`-моста.

`consumer.go` в `handleMessage` создавал span (строка 469), но аналогичного
шага не делал — ни один лог не содержал `trace_id`, из лога нельзя было
перейти к трейсу. Это была несогласованность между двумя половинами
библиотеки, а не просто отсутствующая фича.

**Фикс:** в `consumer.go handleMessage` добавлен локальный логгер `log`,
который при валидном `span.SpanContext()` получает поле `trace_id` (по тому
же паттерну, что уже использовался в `producer.SendMessage`), и все логи
внутри функции переведены на него.

Полноценный переход на context-варианты `slog` (`InfoContext`/`ErrorContext`)
и `otelslog`-мост в рамках этого фикса не делался — это отдельное, более
крупное изменение API логирования библиотеки.

## Что в порядке

- Структурное логирование через `log/slog` — везде.
- Правильный выбор типов метрик: Histogram вместо Summary для latency.
- Span-атрибуты следуют messaging semantic conventions и ограничены по
  кардинальности (`topic`, `partition`, `offset`, `consumer_group`).
- Ошибка не логируется и не возвращается одновременно — top-level логирование
  соблюдено.
