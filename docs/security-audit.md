# Аудит безопасности (2026-07-07)

> **Статус: находки исправлены (2026-07-07).**

Полный аудит `config.go`, `producer.go`, `consumer.go`, `headers.go`, `otel.go`,
`encoding/proto.go`, `example.env`, `README.md` и истории git на предмет
уязвимостей: секреты/credentials, TLS/крипто-конфигурация, инъекции, DoS/
resource exhaustion, утечки в логи, supply-chain (зависимости). Дополнительно
прогнаны `govulncheck ./...` (0 уязвимостей) и `gosec ./...` (см. ниже).

## Находки

### 1. 🔴 High — TLS-соединение по умолчанию не проверяло hostname брокера (CWE-295) — исправлено

**DREAD: ~7.0 (High).** Damage 8, Reproducibility 9, Exploitability 5,
Affected users 9, Discoverability 4.

`TLS.endpointIdentAlgorithm()` (`config.go`) транслирует `Config.TLS` в
librdkafka-параметр `ssl.endpoint.identification.algorithm`, который отвечает
за проверку hostname брокера в TLS-сертификате (RFC 2818). До фикса:

```go
func (t TLS) endpointIdentAlgorithm() string {
	if t.InsecureSkipVerify || t.IdentificationAlgorithm == "" {
		return tlsIdentAlgorithmNone
	}
	return t.IdentificationAlgorithm
}
```

Незаданное (нулевое) значение `TLS.IdentificationAlgorithm` резолвилось в
`"none"` — **точно так же**, как явный `InsecureSkipVerify=true`. Проверено по
документации самого librdkafka (`CONFIGURATION.md`, ключ
`ssl.endpoint.identification.algorithm`): собственное умолчание библиотеки —
**`https`** (проверка hostname включена), а не `none`. Таким образом kafkax не
просто наследовал небезопасное умолчание нижележащей библиотеки — он **активно
понижал** его с secure-by-default `https` до `none` при малейшей невнимательности
пользователя.

**Практическое следствие:** любой пользователь, включивший TLS (`SecurityProtocol:
SSL`/`SASL_SSL` + `TLS.CaCertPath`), но не задавший **отдельно и явно**
`TLS.IdentificationAlgorithm: "https"`, получал соединение, устойчивое к
подмене сертификата другого хоста той же цепочки доверия — классический
MITM-сценарий: атакующий с позицией на пути трафика мог подставить **любой**
валидный (для другого hostname) сертификат от доверенного CA, и клиент принял
бы его, поскольку сверка имени хоста была отключена. Само разделение цепочки
доверия (валидность подписи CA) при этом не отключалось — отключалась только
привязка сертификата к конкретному брокеру.

Существовавший докстринг у поля (`config.go`, до фикса: "Стандартное значение:
'https'") и README (`| TLS.IdentificationAlgorithm | none | ...`) прямо
подтверждают: поведение было **задокументированным**, а не скрытым багом — но
задокументированный небезопасный default всё равно нарушает secure-by-default
и легко упускается при беглом чтении таблицы конфигурации.

**Фикс:** `endpointIdentAlgorithm()` теперь возвращает `"none"` **только** при
явном `InsecureSkipVerify=true`; пустой `IdentificationAlgorithm` резолвится в
`"https"` (константа `tlsIdentAlgorithmHTTPS`), совпадая с собственным
умолчанием librdkafka. Технический повод для подстановки значения вообще
(librdkafka отклоняет пустую строку для этого enum-параметра) сохранён —
изменилось только, **каким** значением её замещать. Обновлены: докстринги
`TLS.IdentificationAlgorithm`/`endpointIdentAlgorithm()`, таблица в README.md,
тест `TestTLS_EndpointIdentAlgorithm` (ранее один из подтестов **утверждал
уязвимое поведение** — "пустой IdentificationAlgorithm → none (безопасное
умолчание)" — эта формулировка сама по себе была неверной и переписана), и
добавлен интеграционный тест `TestBuildProducerKafkaConfig`, проверяющий
итоговое значение непосредственно в `kafka.ConfigMap`, а не только в
изолированном юнит-тесте `endpointIdentAlgorithm()`.

**Важно:** это breaking-change поведения по умолчанию — деплойменты, уже
работающие через `SecurityProtocol=SSL/SASL_SSL` без явного
`IdentificationAlgorithm`, при обновлении начнут **реально проверять** hostname
брокера. Если сертификат брокера не содержит корректный SAN/CN для того
hostname, к которому подключается клиент, соединение перестанет
устанавливаться — это ожидаемо и является целью фикса, но требует отдельного
упоминания в CHANGELOG при следующем релизе.

### 2. 🟡 Medium — паника в фоновых циклах верхнего уровня не перехватывалась (DoS) — исправлено

**DREAD: ~4.8 (Medium).** Damage 6, Reproducibility 5, Exploitability 3,
Affected users 7, Discoverability 3.

`runWorker`/`runPartitionWorker` (по одной горутине на тенанта/партицию)
перехватывают панику через `recover()` в своём завершающем `defer` — паника в
одном воркере просто пересоздаёт этот воркер при следующем сообщении, не
затрагивая остальные. Но три **синглтон**-горутины верхнего уровня, живущие
весь жизненный цикл компонента, такой защиты не имели:

- `KafkaProducer.manageWorkers` → `cleanupInactiveWorkers` (producer.go),
- `KafkaConsumer.runCleanupLoop` → `cleanupInactiveWorkers` (consumer.go),
- `KafkaConsumer.runConsumerLoop` → `processMessage` (consumer.go) — единственная
  из трёх, чья входная точка (`processMessage`) непосредственно управляется
  **содержимым сообщения из Kafka**, а не только внутренним состоянием.

Необработанная паника в горутине по умолчанию завершает **весь процесс** (в
отличие от паники в горутине с `recover()`, которая гасится локально). Из
трёх функций конкретный проходимый сегодня путь к панике в ходе аудита не
найден — находка носит архитектурный, defense-in-depth характер: если баг
когда-либо появится в `processMessage`/`cleanupInactiveWorkers` (например, в
будущей правке, обрабатывающей нестандартные байты сообщения), его блаcт-радиус
сегодня — весь процесс, а не одна фоновая задача. Учитывая, что
`processMessage` управляется содержимым Kafka-сообщений, которые в
мультитенантном/мульти-продьюсерском кластере не всегда доверенный ввод
(см. STRIDE: Denial of Service), несогласованность в покрытии `recover()`
между "воркерами" и "синглтон-циклами" — реальный, хоть и не подтверждённый
конкретным эксплойтом, риск.

**Фикс:** добавлен идентичный `runWorker`/`runPartitionWorker` паттерн
восстановления (`recover()` + `slog.Error` с паникой и стектрейсом) в
`cleanupInactiveWorkers` (оба файла) и `processMessage` (`consumer.go`).
Поведение при отсутствии паники не изменилось — `go test ./... -race`
(`-short`, полный прогон, `-tags=integration`) проходит как до, так и после.

## Без замечаний

- **Инъекции.** Нет SQL/shell/HTML — kafkax не строит команды/запросы из
  пользовательского ввода. `Config.Brokers`/`SecurityProtocol` и т.п. передаются
  в `kafka.ConfigMap` как типизированные значения библиотеки, не как
  конкатенированные строки, интерпретируемые оболочкой.
- **Секреты в логах.** Просмотрены все вызовы `slog`/`logger.*` в `producer.go`/
  `consumer.go` (полный список) — ни в одном не логируются `SASL.Username`,
  `SASL.Password`, пути к ключам TLS, содержимое сообщения (`msg.Value`/`Key`)
  или заголовки. Логируются только некритичные структурные поля: component,
  group, topic, partition, offset, tenant_id (UUID), trace_id, счётчики попыток.
- **Случайность.** `math/rand` нигде не импортируется; `uuid.New()`
  (`github.com/google/uuid`) использует `crypto/rand` внутри.
- **Восстановление после паники в воркерах.** `runWorker`/`runPartitionWorker`
  уже перехватывали панику в пользовательском коде обработчика — паттерн,
  который находка 2 расширила на оставшиеся фоновые циклы.
- **Байты Kafka-заголовков.** Подтверждено в исходниках `confluent-kafka-go/v2`
  (`C.GoBytes` при разборе `msg.Headers`) — каждое сообщение получает свежий,
  скопированный из C-памяти Go-слайс; риска обращения к чужой/переиспользуемой
  памяти через `Headers.Get()`/`fromKafkaHeaders` нет (см. также
  `docs/safety-audit.md`).
- **Supply chain.** Зависимости — официальные, известные пакеты
  (`confluentinc`, `google.golang.org`, `go.opentelemetry.io`, `go.uber.org`),
  без обфусцированных/тайпсквоттинг-подобных имён; `go.sum` присутствует и не
  обходится флагами `-insecure`.

## Отмеченные наблюдения (не в рамках фикса)

- **`SASL_PLAINTEXT` разрешает передачу SASL-credentials по незашифрованному
  соединению.** `Config.Validate()` требует `Username`/`Password` одинаково
  для `SASL_PLAINTEXT` и `SASL_SSL`, не предупреждая, что первый вариант
  передаёт SASL-хендшейк (для механизма `PLAIN` — включая пароль в открытом
  виде) по TCP без TLS. Это осознанный, иногда легитимный выбор оператора
  (например, внутри уже изолированного/зашифрованного на другом уровне
  сегмента сети) — не баг библиотеки, а штатная опция протокола Kafka.
  Библиотека не должна запрещать валидную конфигурацию, которую сам Kafka
  разрешает — оставлено как задокументированный риск, а не исправлено кодом.
- **Неограниченный рост горутин-воркеров по TenantID/(topic,partition).**
  Уже разобрано в `docs/concurrency-audit.md` как наблюдение, релевантное
  скорее resource-exhaustion/DoS, чем корректности конкурентного кода —
  быстрый поток уникальных `TenantID` в `SendMessage` теоретически может расти
  быстрее, чем успевает работать TTL-уборка. Не находка этого прохода, но
  стоит учитывать при нагрузочном тестировании/капасити-планировании.
- **`encoding.UnmarshalProto`** десериализует байты, которые в топике с
  недоверенными продьюсерами могут быть частично контролируемы третьей
  стороной. `proto.Unmarshal` не даёт отдельной защиты от больших/глубоко
  вложенных сообщений сверх размера входных `data` — но размер `data`
  уже ограничен на уровне транспорта (`Consumer.MaxBytes`, по умолчанию
  10 МБ) до того, как достигает `UnmarshalProto`. Отдельного лимита в самой
  функции нет и не добавлен — граница доверия (какие продьюсеры считаются
  доверенными) находится на уровне ACL Kafka-кластера, вне периметра kafkax.
