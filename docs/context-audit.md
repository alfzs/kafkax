# Аудит context.Context (2026-07-07)

> **Статус: все находки исправлены (2026-07-07).**

Аудит использования `context.Context` в `consumer.go`, `producer.go`, `otel.go`,
`headers.go`, `config.go` на соответствие стандартным практикам (propagation,
cancellation, `ctx` как первый параметр, значения в контексте, `WithoutCancel`).

## Находки

### 1. ✅ Докстринг `NewKafkaProducer` обещает то, чего код не делает — исправлено

`producer.go:92-93`:

> ctx используется как родительский контекст продюсера: его отмена эквивалентна
> вызову Close. Для управляемого завершения предпочтительнее явный вызов Close.

Это неверно. `p.ctx` действительно является потомком переданного `ctx`
(`producer.go:165`), и его отмена останавливает `manageWorkers` (`producer.go:538`)
и переводит `runWorker` каждого тенанта в drain (`producer.go:376`). Но
**ничто не слушает `p.ctx.Done()`, чтобы вызвать `Flush` и `p.producer.Close()`**
— это происходит только внутри explicit `Close()` (`producer.go:578-616`). Нет
горутины-наблюдателя, которая по отмене `ctx` довела бы дело до конца.

Практическое следствие: если вызывающий код полагается на докстринг и просто
отменяет переданный в `NewKafkaProducer` контекст (например, на сигнал
завершения), не вызывая `Close()`:
- воркеры корректно остановятся (drain),
- но `p.producer.Flush()` не будет вызван — сообщения, ушедшие в очередь
  librdkafka, но не подтверждённые, не гарантированно долетят;
- `p.producer.Close()` не будет вызван — соединение/файловые дескрипторы
  librdkafka останутся открытыми до конца процесса.

Для сравнения, `KafkaConsumer.Start` описывает то же самое честно
(`consumer.go:270-272`): "его отмена равносильна вызову Stop, **но без**
graceful drain и вызова consumer.Close" — и код это подтверждает (в `Stop()`
такого наблюдателя тоже нет, но комментарий об этом не врёт).

**Фикс:** вместо ослабления докстринга выбран более сильный вариант — код
приведён в соответствие с исходным обещанием. В `NewKafkaProducer` добавлена
горутина-наблюдатель за переданным `ctx` (не за `p.ctx` — иначе она бы
триггерилась и от собственного `p.cancel()` внутри explicit `Close()`):

```go
go func() {
    select {
    case <-ctx.Done():
        p.Close()
    case <-p.closed:
    }
}()
```

Наблюдатель намеренно не входит в `p.wg`: `Close()` дожидается `p.wg.Wait()`,
и если бы наблюдатель, вызывающий сам `Close()`, был частью той же группы,
это был бы либо self-deadlock, либо (в данном случае, благодаря отдельному
таймауту в `Close()`) ложное "Shutdown timed out" при каждом обычном explicit
`Close()`.

Также добавлено поле `KafkaProducer.closed chan struct{}`, закрываемое в
начале `Close()` сразу после `CompareAndSwap` на `isStopping`. Наблюдатель
слушает именно его, а не `p.ctx.Done()` — иначе при каждом explicit `Close()`
(которым `p.cancel()` вызывается сам) наблюдатель ловил бы это как "внешняя
отмена" и пытался вызвать `Close()` повторно (безвредно благодаря
идемпотентности, но с лишним warning-логом на каждый штатный `Close()`).
Слушание `p.closed` устраняет и это, и утечку наблюдающей горутины в самом
частом сценарии — `context.Background()` при создании продюсера и
управление жизненным циклом только через explicit `Close()`: в этом случае
горутина выходит по `p.closed`, а не виснет на `ctx.Done()`, который никогда
не сработает.

Докстринг обновлён, чтобы отражать фактическое поведение: отмена `ctx`
теперь действительно эквивалентна `Close()`, explicit-вызов остаётся
предпочтительным только потому, что он даёт возможность синхронно дождаться
завершения shutdown.

Проверено `go build`, `go vet`, `go test ./... -race` — без падений и без
предупреждений детектора гонок.

### 2. ✅ `drainCtx` в `runPartitionWorker` собран из `context.Background()`, а не `context.WithoutCancel` — исправлено

`consumer.go:472`:

```go
case <-worker.ctx.Done():
    drainCtx, cancel := context.WithTimeout(context.Background(), c.config.GracefulTimeout)
```

Это ровно тот случай, для которого существует `context.WithoutCancel` (Go
1.21+): фоновая работа, которая обязана пережить отмену родителя, но должна
сохранить значения контекста. Сейчас код собирает `drainCtx` с нуля от
`context.Background()`, теряя всё, что могло быть положено в контекст вызовом
`Start(ctx)` (baggage, значения из `context.WithValue` и т.п. — если такие
появятся у пользователей библиотеки).

Сегодня это не ломает ничего наблюдаемого, потому что сам kafkax не кладёт
значения в `ctx` через `WithValue`, а trace context для спана извлекается из
Kafka-заголовков (`c.propagator.Extract`), а не из значений `ctx`. Но это
хрупкое предположение: любой пользователь библиотеки, положивший что-то в
контекст перед `Start(ctx)`, тихо потеряет это значение на любых сообщениях,
дошедших до voркера в момент drain.

**Фикс:** `consumer.go:472` переведён на

```go
drainCtx, cancel := context.WithTimeout(context.WithoutCancel(worker.ctx), c.config.GracefulTimeout)
```

`WithoutCancel` не зависит от того, что `worker.ctx` уже отменён — `Done()`
результирующего контекста в любом случае не сработает от родителя, только от
таймаута.

### 3. ✅ `SendMessage` не возвращает `ctx.Err()` при отмене — несогласованность внутри пакета — исправлено

`producer.go:283-284` и `producer.go:294-295`:

```go
case <-ctx.Done():
    return errors.New("context canceled")
...
case <-ctx.Done():
    return errors.New("context canceled while queuing")
```

`produce()` в том же файле для эквивалентного случая делает правильно
(`producer.go:513-517`):

```go
case <-msg.Ctx.Done():
    ...
    err = msg.Ctx.Err()
    return err
```

Возврат сконструированной через `errors.New` строки вместо `ctx.Err()` ломает
`errors.Is(err, context.Canceled)` / `errors.Is(err, context.DeadlineExceeded)`
для потребителей библиотеки — им приходится матчиться по тексту ошибки, чтобы
различить отмену и таймаут дедлайна. Это также единственное место в пакете,
где для отмены контекста не используется `ctx.Err()`.

**Фикс:** оба места в `SendMessage` (`producer.go`) переведены на
`fmt.Errorf("context canceled...: %w", ctx.Err())`, сохранив прежний текст
ошибки через `%w`-обёртку вокруг `ctx.Err()`.

## Без замечаний

- Все функции, принимающие `context.Context`, делают это первым параметром
  (`Start`, `handleMessage`, `NewKafkaProducer`, `SendMessage`).
- `message.Ctx` (поле, а не параметр) — оправданное исключение: `message` это
  элемент очереди воркера, передаваемый через канал в другую горутину, а не
  обычный вызов функции; это стандартный паттерн для worker pool.
- `context.WithValue` нигде не используется — рисков коллизии ключей нет.
- `cancel()` вызывается на всех путях для каждого `WithCancel`/`WithTimeout`
  (включая `defer cancel()` в drain-цикле консьюмера).
- `context.Background()` в `NewKafkaConsumer` (`consumer.go:189`) — временная
  заглушка до `Start()`, задокументированная и безопасная: горутины до
  `Start()` не запускаются, поэтому "настоящий" `ctx` подменяет её раньше,
  чем она где-либо используется.
- `context.Background()` в `metrics....Add(context.Background(), ±1)` при
  создании/уничтожении воркера (`producer.go:345,365`, `consumer.go:429,460`)
  — приемлемо: это события жизненного цикла воркера, не привязанные к
  конкретному запросу/трейсу, терять здесь нечего.

## Отдельно: хранение ctx в полях структур (`p.ctx`, `c.ctx`, `worker.ctx`)

Формально нарушает правило "никогда не храните context в структуре" — но это
осознанный архитектурный выбор для контекста жизненного цикла долгоживущего
компонента (аналог `BaseContext` у `http.Server`), а не request-scoped
контекст операции. Риск невысокий, поскольку из этих полей нигде не читаются
`Value()` — используется только `Done()`/`Err()` для сигнала остановки. Не
считаю это находкой, требующей фикса, но стоит явно закомментировать в местах
объявления полей (`ctx context.Context`), что это lifecycle-контекст компонента,
а не контекст текущей операции — чтобы будущие правки не начали класть туда
request-scoped значения по ошибке.
