# 04. Ошибки и контракт API

**Статус:** 🟡 частично — 4 из 12
**Источник:** аудит пакета kafkax, 2026-07-29
**Зависит от:** 06-tests, 08-style-docs

## Контекст

Ошибки пакета делятся на две неравные части: там, где сентинелы есть, контракт работает, — а на
двух путях, где потребитель **обязан** среагировать (недослитый буфер продюсера и проваленный
финальный коммит), различить исход можно было только через `strings.Contains`. Рядом — `Config`
без годного нулевого значения и без `DefaultConfig()`, документированный разбор списка ошибок
валидации, ломающийся ровно в конструкторе, и контракт владения памятью `IncomingMessage`,
который не соответствует коду и внутренне противоречив.

Волной 2 закрыты RF-API-01, RF-API-02, RF-API-03, RF-API-04 — сентинелы завершения и настройки,
`DefaultConfig()`. Волной 1 не тронуто ничего, кроме мёртвой ссылки `SubscribeAll` в RF-API-12
(она же [08](08-style-docs.md) RF-DOCS-08). Остаются открытыми RF-API-05, RF-API-06, RF-API-07 —
RF-API-11 и остаток RF-API-12. Сводка — в [README.md](README.md).

## Задачи

### RF-API-01 · P1 · Ошибки завершения неклассифицируемы

**Статус:** 🟢 закрыто волной 2
**Прежний ID:** С1
**Где:** `producer.go:339`, `producer.go:353`, `consumer.go:994`.

**Проблема**

`"flush budget exhausted"`, `"flushing %d buffered records"`, `"committing marked offsets"` не
привязаны к сентинелам. В `errors.go` нет ни `ErrFlushIncomplete`, ни `ErrCommitFailed`.

**Чем грозит.** Это ровно те два случая, где потребитель **обязан** среагировать (алерт, повтор,
отказ от завершения) — а различить их можно только через `strings.Contains`. `defer
producer.Close()` теряет сообщения молча, след только WARN в логе.

**Решение**

`ErrFlushIncomplete`, `ErrCommitFailed`; при желании — типизированная
`*FlushError{Remaining int64}`.

Оба сентинела заведены в `errors.go` (`:87` и `:95`). Обе ветки `flush` возвращают
`ErrFlushIncomplete` — исчерпанный бюджет (`producer.go:378`) и таймаут с остатком в буфере
(`:393`); финальный коммит в `shutdown` — `fmt.Errorf("%w: %w", ErrCommitFailed, commitErr)`
(`consumer.go:1365`), то есть с сохранённой причиной.

Типизированную `*FlushError` заводить не стали: единственное её поле — число оставшихся записей,
которое уже есть и в тексте, и в записи WARN, а публичный тип пришлось бы поддерживать вечно ради
величины, по которой не принимают решений. Само число из текста ошибки не убрано, хотя для
группировки в APM оно высококардинально (см. RF-API-12).

**Критерий приёмки**

- [x] `TestProducerCloseBoundedByGracefulTimeout`: `Close` на недоступном брокере возвращает
      ошибку, опознаваемую через `errors.Is(err, ErrFlushIncomplete)`
- [x] `TestStopReportsFailedFinalCommit`: кластер гасится после обработки, но до `Stop`;
      `Stop` возвращает `ErrCommitFailed`, и причина развёрнута рядом с сентинелом
- [x] `TestSentinelsAreDistinct` и `TestSentinelsSurviveWrapping` покрывают оба новых сентинела
- [x] Второй тест закрывает и часть [06](06-tests.md) RF-TEST-02

**Риски:** сентинелы — часть публичного контракта, переименование или удаление ломает потребителей
молча (`errors.Is` просто перестанет находить). Откат правки возвращает `strings.Contains` как
единственный способ различить два исхода завершения.

### RF-API-03 · P1 · Ошибки валидации непроверяемы; документированный разбор списка ломается в конструкторе

**Статус:** 🟢 закрыто волной 2
**Прежний ID:** С3
**Где:** `config.go:301-303`, `producer.go:89`, `consumer.go:255`.

**Проблема**

1. ~25 ошибок валидации без общего сентинела — `errors.Is(err, ErrInvalidConfig)` невозможен.
2. Godoc `Validate` обещает разворот через `errors.Unwrap() []error`. Конструкторы оборачивают
   joined-ошибку **ещё раз** (`fmt.Errorf("invalid producer config: %w", err)`) — у результата
   `Unwrap() error`, а не `[]error`. **Документированный приём на ошибке `NewKafkaProducer` не
   работает.**

**Решение**

Аудит предлагал `ErrInvalidConfig` + `errors.Join(append([]error{ErrInvalidConfig}, errs...)...)`;
в конструкторах не оборачивать повторно. **Закрыто волной 2, но не предложенным способом.**

Подмешивать сентинел в `errors.Join` нельзя: тогда он вылезает первым элементом `Unwrap() []error`,
и код, печатающий список претензий пользователю, начинает его строкой «invalid configuration».
Вместо этого заведён тип-агрегат `configError{subject, errs}` (`config.go:396`) с `Unwrap() []error`
(`:418` — только претензии к полям) и `Is(target) bool` (`:424` — отвечает `true` на
`ErrInvalidConfig`). Конструкторы отдают его как есть — обёртка через `fmt.Errorf` подменила бы
`Unwrap() []error` на `Unwrap() error`. Сам сентинел объявлен в `errors.go:104`.

**Критерий приёмки**

- [x] `TestValidationErrorsCarryInvalidConfigSentinel` проверяет обе стороны на всех трёх входах
      (`Validate`, `NewKafkaProducer`, `NewKafkaConsumer`): сентинел опознаётся через `errors.Is`,
      список разворачивается через `Unwrap() []error` и содержит ≥2 претензии
- [x] тот же тест: сентинела **нет** ни в одном элементе списка — иначе перечень полей начинался
      бы строкой «invalid configuration»
- [x] `TestValidConfigProducesNoError` закрывает ловушку nil-указателя в интерфейсе ошибки:
      `newConfigError("config", nil) == nil`; без неё ни один валидный конфиг не прошёл бы
      конструктор

**Риски:** `configError` неэкспортирован — потребитель работает с ним только через `errors.Is` и
`errors.Unwrap() []error`, и это единственный поддерживаемый способ. Любая обёртка результата через
`fmt.Errorf` в конструкторах снова сломает документированный разбор списка: `Unwrap() []error`
превратится в `Unwrap() error`.

### RF-API-04 · P1 · У `Config` нет годного нулевого значения и способа получить дефолты из кода

**Статус:** 🟢 закрыто волной 2
**Прежний ID:** С4
**Где:** `config.go:48-292`; `DefaultConfig` в пакете отсутствует.

**Проблема**

Все дефолты живут только в тегах `env-default` и материализуются лишь через `cleanenv`. `Config`,
собранный литералом в Go — полностью поддерживаемый путь, — даёт ~15 ошибок валидации.

**Чем грозит.** Тесты потребителя и любая программная конфигурация обязаны знать все 41 значение
по умолчанию наизусть.

**Решение**

`func DefaultConfig() Config` — чистое добавление, ломать ничего не нужно; плюс тест-сверка
возвращаемых значений с тегами `env-default`.

`DefaultConfig()` возвращает все 29 значений из тегов `env-default`. `Brokers`, `ClientID` и
`Consumer.Group` оставлены пустыми намеренно: умолчание у группы означало бы, что два забывших её
задать сервиса молча делят один assignment.

Значения продублированы в коде, а не вытащены рефлексией: разбор строк тега в рантайме стоил бы
парсинга на каждое поле и отдавал бы вызывающему ошибку разбора собственного тега. Плата за дубль —
`TestDefaultConfigMatchesStructTags`: обход по структуре сверяет обе стороны, поэтому поле с тегом,
но без строки в `DefaultConfig`, валит сборку тестов, а не продакшен потребителя. Проверка
двусторонняя — поле **без** тега обязано остаться нулевым.

**Критерий приёмки**

- [x] `TestDefaultConfigMatchesStructTags`: обход по структуре сверяет `DefaultConfig()` с тегами
      `env-default` в обе стороны — расхождение валит тесты
- [x] `TestDefaultConfigIsUsableAfterFillingRequiredFields`: `DefaultConfig()` плюс `Brokers`,
      `ClientID`, `Consumer.Group` проходит `Validate()` без ошибок
- [x] `TestDefaultConfigWithoutRequiredFieldsFailsValidation`: три намеренно пустых поля
      по-прежнему обязательны

**Риски:** дубль значений в коде и в тегах — источник расхождения, и держится он только тестом;
если `TestDefaultConfigMatchesStructTags` удалят, новое поле молча уедет с нулевым значением.
Само добавление обратной совместимости не ломает.

### RF-API-05 · P1 · Контракт владения памятью `IncomingMessage` не соответствует коду и внутренне противоречив

**Статус:** 🔴 открыто
**Прежний ID:** С5
**Где:** `consumer.go:25-27` (godoc), `consumer.go:654` и `:686` (нарушение), `config.go:89-103`;
**плюс blockquote в README, раздел «Быстрый старт»**.

**Проблема**

Godoc: «`Key`, `Value`, `Headers` живут ровно столько, сколько длится вызов обработчика».

По исходникам franz-go v1.21.5 переиспользование буферов включается **только** через
`kgo.WithPools` (`kgo/source.go:1765-1779` — put-back лишь при зарегистрированном
`PoolDecompressBytes`; `Record.Recycle()` в `kgo/pools.go:122` — no-op без `r.Context`). kafkax
`WithPools` не вызывает → буферы обычные, GC-управляемые. Собственный код это подтверждает:
`dispatch` (`:464-478`) держит до `MessageQueueSize` батчей в канале.

**Противоречие внутри пакета:** `resolveFailure` передаёт тот же `msg` в `OnMessageSkipped`
**после** возврата из `ProcessMessage` (`:654` → `:686`) — библиотека по собственным правилам
отдаёт просроченные буферы.

Отдельно: `Config.ExtraOpts` позволяет протащить `kgo.WithPools`, после чего правило станет
правдой, а `Recycle()` kafkax не вызывает — пулинг выродится в отсутствие возврата памяти.

*Проверено вручную: `WithPools`/`Recycle` не вызываются в репозитории нигде.*

**Решение**

Привести godoc и README к коду: «срез разделяется с записью franz-go; пулинг не включён, но
мутировать нельзя — те же срезы уходят в повторы и в `OnMessageSkipped`». Продублировать в godoc
`OnMessageSkipped`.

**Критерий приёмки**

- [ ] Godoc `IncomingMessage` (`consumer.go:25-27`) не утверждает, что срезы живут только на время
      вызова обработчика
- [ ] Тот же текст продублирован в godoc `OnMessageSkipped` (`config.go:89-103`) и в blockquote
      README «Быстрый старт»
- [ ] Ограничение «мутировать нельзя» названо явно, с причиной: те же срезы уходят в повторы и
      в `OnMessageSkipped`
- [ ] Поведение `ExtraOpts` + `kgo.WithPools` либо задокументировано как неподдерживаемое, либо
      закрыто вызовом `Recycle()`

**Риски:** правка документации меняет обещание в сторону ослабления — потребители, копировавшие
`Value` из-за прежнего godoc, ничего не сломают. Обратное неверно: если оставить как есть, кто-то
положится на буквальное «живут ровно столько» и мутирует срез.

### RF-API-06 · P1 · `encoding.EncodeKey(parts ...any)` — API, который сам документирует свою ловушку

### RF-API-08 · P2 · Контракт вызова `OnMessageSkipped` не документирован

**Прежний ID:** У2

### RF-API-10 · P2 · `Start` после `Stop` возвращает «уже запущен» вместо «закрыт»

**Статус:** 🔴 открыто
**Прежний ID:** У4
**Где:** `consumer.go:321-341`, `errors.go:34-38`.

**Проблема**

Проверено при закрытии волны 1 и намеренно не тронуто: `Start` взводит `started` до проверки
`stopping`, поэтому `Start` → `Stop` → `Start` по-прежнему даёт `ErrConsumerStarted`.
`ErrConsumerClosed` приходит только когда `Stop` случился раньше первого `Start`.

`started` — флаг «когда-либо стартовал». После `Stop` он остаётся `true` → повторный `Start`
падает на CAS с `ErrConsumerStarted` (`:324`). До проверки `stopping` (`:337`) доходит только если
`Stop` был раньше `Start`. Godoc `Start` честно пишет «не перезапускается» — расхождение осознано в
тексте, но не в коде.

Смежное: `AddHandler` на консьюмере, остановленном без запуска, **молча успешен** (`:298`
проверяет только `started`).

*Проверено вручную.*

**Решение**

Проверять `stopping` **до** CAS, возвращать `ErrConsumerClosed`; ту же проверку в `AddHandler`.

**Критерий приёмки**

- [ ] `Start` → `Stop` → `Start` возвращает `ErrConsumerClosed`, а не `ErrConsumerStarted`
- [ ] `AddHandler` на остановленном консьюмере возвращает `ErrConsumerClosed`, а не успех
- [ ] `TestStartContract` и `TestAddHandlerContract` дополнены обоими случаями
- [ ] `TestStopWithoutStart` продолжает проходить: `Stop` до `Start` по-прежнему не ошибка

**Риски:** меняется наблюдаемое поведение двух публичных методов — код, различающий
`ErrConsumerStarted` и `ErrConsumerClosed`, получит другую ветку. `AddHandler`, который сейчас
молча успешен, начнёт возвращать ошибку: потребитель, регистрирующий обработчики после `Stop`,
это заметит.

### RF-API-11 · P2 · `*kerr.Error` вшит в публичный контракт ошибок

**Статус:** 🔴 открыто
**Прежний ID:** У5
**Где:** `errors.go:22-26`, `doc.go:99-103` — godoc прямо предписывает `errors.As` до `*kerr.Error`.

**Проблема**

Потребители получают жёсткую зависимость на `franz-go/pkg/kerr`. Смена клиента (один переход уже
пережит) сломает логику у каждого потребителя, и **компилятор не покажет** — `errors.As` просто
перестанет находить тип.

**Решение**

Либо свой `DeliveryError{Topic, Code, Retriable, Err}`, либо явно зафиксировать в документации,
что `kerr` — часть контракта v2.

**Критерий приёмки**

- [ ] Выбран один из двух вариантов и записан в `doc.go` явным утверждением, а не умолчанием
- [ ] Если заводится `DeliveryError` — `TestProduceErrorKeepsBrokerError` и
      `TestProduceErrorUnwrapsWrappedBrokerError` переписаны на него, а `*kerr.Error` остаётся
      достижим через `errors.As` в цепочке
- [ ] Если фиксируется `kerr` — README и `doc.go` называют `franz-go/pkg/kerr` частью
      публичного контракта v2

**Риски:** первый вариант — новый публичный тип, который придётся поддерживать при любой смене
клиента; второй — сознательная фиксация чужого типа в контракте, то есть блокировка смены клиента
без мажорной версии.

### RF-API-12 · P3 · Мелочи контракта ошибок и именования

**Статус:** 🟡 закрыто наполовину волной 1
**Прежний ID:** Мелочи
**Где:** `consumer.go:682`, `:288`, `:29-34`, `:252`, `:322`; `errors.go:28-32`, `:46`;
`producer.go:199`, `:353`; `middleware.go:61-64`; `config.go:518`, `:322-522`.

**Проблема**

* **Ни одной типизированной ошибки** — координаты сообщения только текстом: ошибка `SendMessage` не
  несёт `Topic`, ошибка финального коммита не несёт партиций.
* **Статтеры в именах:** `kafkax.KafkaProducer` / `NewKafkaConsumer` — «kafka» дважды. Хорошие
  имена заняты **секциями конфигурации**: `kafkax.Producer`, `kafkax.Consumer`. →
  `Producer`/`Consumer` для типов, `ProducerConfig`/`ConsumerConfig` для секций.
* **`ErrHandlerPanic` переиспользован для паники хука, причина теряется** — `consumer.go:682`:
  `fmt.Errorf("on message skipped: %w", ErrHandlerPanic)`, значение `recover()` не попадает
  (в `callHandler:770` есть `%v` от `r`). Godoc сентинела (`errors.go:28-32`) для этого пути
  неверен.
* ~~**Мёртвая ссылка в godoc ошибки**~~ — `errors.go:46`: «…который `SubscribeAll` передал бы в
  `ConsumeTopics`». `SubscribeAll` в репозитории нет (единственное вхождение — эта строка).
  **Закрыто волной 1:** godoc `ErrEmptyTopic` теперь называет `AddHandler` и `Start`.
* **Пять разных стилей префикса операции:** `invalid producer config:` (`producer.go:89`),
  `new_kafka_consumer:` (`consumer.go:252`, snake_case!), `start:` (`:322`),
  `send message:` (`producer.go:199`), `add handler:` (`consumer.go:288`).
* **Рассинхрон словаря:** `PublishRequest` / `IncomingMessage` / `SendMessage` — три слова на одну
  сущность.
* **Проверка длины ключа дублируется** вместо вызова `ValidateKeyLength` — `middleware.go:61-64` vs
  `encoding/key.go:116-127`. См. [08-style-docs.md](08-style-docs.md) RF-DOCS-07.
* `config.go:518` — единственная ошибка валидации без `got %v`.
* `config.go:322-522` — ошибки называют поле yaml-путём; для `Config`, собранного в Go, нужен
  Go-путь.
* `consumer.go:29-34` — у `IncomingMessage` задокументирован только `Timestamp`;
  `Offset`/`Partition`/`Key` — нет.
* `producer.go:353` — число записей внутри текста ошибки высококардинально для группировки в APM.

**Решение**

Мёртвая ссылка закрыта волной 1: godoc `ErrEmptyTopic` называет `AddHandler` и `Start` вместо
несуществующего `SubscribeAll`.

Остальное: свести префиксы операций к одному стилю; починить godoc `ErrHandlerPanic` для пути
хука и донести значение `recover()`; выровнять словарь `PublishRequest`/`IncomingMessage`;
заменить дубль проверки длины ключа вызовом `ValidateKeyLength`; дописать `got %v` в
`config.go:518` и Go-пути полей в тексты валидации; задокументировать `Offset`/`Partition`/`Key`
у `IncomingMessage`. Число записей из текста `producer.go:353` не убрано намеренно — см.
RF-API-01.

**Критерий приёмки**

- [x] `SubscribeAll` не встречается в репозитории ни разу; godoc `ErrEmptyTopic` называет
      `AddHandler` и `Start`
- [ ] Все префиксы операций в текстах ошибок — в одном стиле, `new_kafka_consumer:` в snake_case
      не встречается
- [ ] `consumer.go:682` доносит значение `recover()` в текст ошибки, как `callHandler:770`;
      godoc `errors.go:28-32` описывает оба пути
- [ ] `middleware.go` вызывает `encoding.ValidateKeyLength`, дубля проверки нет;
      `TestMatchKeyMiddleware` и `TestValidateKeyLength_*` проходят
- [ ] Каждая ошибка валидации содержит `got %v` — включая `config.go:518`

**Риски:** тексты ошибок меняются массово; контрактом они не объявлены (`errors.go:5-6`), но
тесты потребителей, сверяющие строки, сломаются. Переименование `KafkaProducer`/`KafkaConsumer` —
ломающее изменение публичного API и требует отдельного решения, не «мелочи».

## Что осознанно не делаем

- **Не подмешиваем `ErrInvalidConfig` в `errors.Join`** — предложенный аудитом способ отвергнут:
  сентинел вылезал бы первым элементом `Unwrap() []error`, и код, печатающий список претензий
  пользователю, начинал бы его строкой «invalid configuration». Вместо него — тип-агрегат
  `configError` с `Is(target)` (RF-API-03).
- **Не оборачиваем результат валидации в конструкторах через `fmt.Errorf`** — обёртка подменила бы
  `Unwrap() []error` на `Unwrap() error`, то есть сломала бы документированный разбор списка ровно
  там, где он и был сломан до правки (RF-API-03).
- **Не заводим типизированную `*FlushError{Remaining int64}`** — единственное её поле уже есть и в
  тексте ошибки, и в записи WARN, а публичный тип пришлось бы поддерживать вечно ради величины, по
  которой не принимают решений (RF-API-01).
- **Не убираем число оставшихся записей из текста ошибки `flush`** — для группировки в APM оно
  высококардинально, но это единственное место, где число вообще доступно вызывающему
  (RF-API-01, RF-API-12).
- **Не вытаскиваем дефолты рефлексией из тегов `env-default`** — разбор строк тега в рантайме
  стоил бы парсинга на каждое поле и отдавал бы вызывающему ошибку разбора собственного тега;
  дубль в коде стережёт `TestDefaultConfigMatchesStructTags` (RF-API-04).
- **Не даём умолчания `Brokers`, `ClientID` и `Consumer.Group`** — умолчание у группы означало бы,
  что два забывших её задать сервиса молча делят один assignment (RF-API-04).
