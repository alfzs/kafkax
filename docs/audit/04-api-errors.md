## С1 [СЕРЬЁЗНО] Ошибки завершения неклассифицируемы

**Где:** `producer.go:339`, `producer.go:353`, `consumer.go:994`.

`"flush budget exhausted"`, `"flushing %d buffered records"`, `"committing marked offsets"` не
привязаны к сентинелам. В `errors.go` нет ни `ErrFlushIncomplete`, ни `ErrCommitFailed`.

**Чем грозит.** Это ровно те два случая, где потребитель **обязан** среагировать (алерт, повтор,
отказ от завершения) — а различить их можно только через `strings.Contains`. `defer producer.Close()`
теряет сообщения молча, след только WARN в логе.

**Исправление.** `ErrFlushIncomplete`, `ErrCommitFailed`; при желании — типизированная
`*FlushError{Remaining int64}`.

## С2 [СЕРЬЁЗНО] Повторная регистрация обработчика — без сентинела

**Где:** `consumer.go:306` — единственная ошибка `AddHandler` без сентинела (у трёх соседних он
есть).

`consumer_test.go:547` уже проверяет `strings.Contains(err.Error(), "already registered")` — тест
зафиксировал строку как контракт, хотя `errors.go:5-6` объявляет текст **не** частью контракта.

**Исправление.** `ErrDuplicateHandler`; тест переписать на `errors.Is`. *Проверено вручную.*

## С3 [СЕРЬЁЗНО] Ошибки валидации непроверяемы; документированный разбор списка ломается в конструкторе

**Где:** `config.go:301-303`, `producer.go:89`, `consumer.go:255`.

1. ~25 ошибок валидации без общего сентинела — `errors.Is(err, ErrInvalidConfig)` невозможен.
2. Godoc `Validate` обещает разворот через `errors.Unwrap() []error`. Конструкторы оборачивают
   joined-ошибку **ещё раз** (`fmt.Errorf("invalid producer config: %w", err)`) — у результата
   `Unwrap() error`, а не `[]error`. **Документированный приём на ошибке `NewKafkaProducer` не
   работает.**

**Исправление.** `ErrInvalidConfig` + `errors.Join(append([]error{ErrInvalidConfig}, errs...)...)`;
в конструкторах не оборачивать повторно.

## С4 [СЕРЬЁЗНО] У `Config` нет годного нулевого значения и способа получить дефолты из кода

**Где:** `config.go:48-292`; `DefaultConfig` в пакете отсутствует.

Все дефолты живут только в тегах `env-default` и материализуются лишь через `cleanenv`. `Config`,
собранный литералом в Go — полностью поддерживаемый путь, — даёт ~15 ошибок валидации.

**Чем грозит.** Тесты потребителя и любая программная конфигурация обязаны знать все 41 значение
по умолчанию наизусть.

**Исправление.** `func DefaultConfig() Config` — чистое добавление, ломать ничего не нужно; плюс
тест-сверка возвращаемых значений с тегами `env-default`.

## С5 [СЕРЬЁЗНО] Контракт владения памятью `IncomingMessage` не соответствует коду и внутренне противоречив

**Где:** `consumer.go:25-27` (godoc), `consumer.go:654` и `:686` (нарушение), `config.go:89-103`;
**плюс blockquote в README, раздел «Быстрый старт»**.

Godoc: «`Key`, `Value`, `Headers` живут ровно столько, сколько длится вызов обработчика».

По исходникам franz-go v1.21.5 переиспользование буферов включается **только** через
`kgo.WithPools` (`kgo/source.go:1765-1779` — put-back лишь при зарегистрированном
`PoolDecompressBytes`; `Record.Recycle()` в `kgo/pools.go:122` — no-op без `r.Context`). kafkax
`WithPools` не вызывает → буферы обычные, GC-управляемые. Собственный код это подтверждает:
`dispatch` (`:464-478`) держит до `MessageQueueSize` батчей в канале.

**Противоречие внутри пакета:** `resolveFailure` передаёт тот же `msg` в `OnMessageSkipped`
**после** возврата из `ProcessMessage` (`:654` → `:686`) — библиотека по собственным правилам
отдаёт просроченные буферы.

Отдельно: `Config.ExtraOpts` позволяет протащить `kgo.WithPools`, после чего правило станет
правдой, а `Recycle()` kafkax не вызывает — пулинг выродится в отсутствие возврата памяти.

**Исправление.** Привести godoc и README к коду: «срез разделяется с записью franz-go; пулинг не
включён, но мутировать нельзя — те же срезы уходят в повторы и в `OnMessageSkipped`».
Продублировать в godoc `OnMessageSkipped`.

*Проверено вручную: `WithPools`/`Recycle` не вызываются в репозитории нигде.*

## С6 [СЕРЬЁЗНО] `encoding.EncodeKey(parts ...any)` — API, который сам документирует свою ловушку

**Где:** `encoding/key.go:35-74`, godoc `:81-88`.

Ключ из `...any` с рантайм-свитчем по четырём типам. Godoc `MatchKey` прямым текстом описывает
отказ: «опечатка в типе (`int` вместо `int64`)» — и лечится он паникой, а не системой типов.
`EncodeKey(42)` компилируется. Ошибки `EncodeKey` не привязаны к сентинелу.

**Исправление.** Типизированный билдер `encoding.NewKey().UUID(x).Str(y).Int64(z).Build()`;
минимум — `ErrUnsupportedKeyPart`.

## У1 [УМЕРЕННО] `produceError` теряет причину у двух из четырёх исходов

**Где:** `producer.go:252-275`. Ветки `ErrDeliveryTimeout` и `ErrProducerClosed` возвращают голый
сентинел. Четыре разных формы у одной функции; `SendMessage` добавляет пятую.

Не различить «наш `context.DeadlineExceeded`» от «`kgo.ErrRecordTimeout`» — разные диагнозы.

**Исправление.** `fmt.Errorf("send message: %w: %w", ErrDeliveryTimeout, err)` во всех ветках.

## У2 [УМЕРЕННО] Контракт вызова `OnMessageSkipped` не документирован

**Где:** `config.go:89-103`.

Godoc объясняет семантику возврата, но молчит о вызове. По коду (`consumer.go:637-687`): вызывается
синхронно из горутины партиционного воркера; `ctx` = `msgCtx`, отменяется при жёсткой остановке и
по таймауту `awaitWorkers` (`:924`); блокировка держит партицию и съедает `RebalanceTimeout`;
паника перехватывается и трактуется как «не забрал». У `OnPanic` (`config.go:85-86`) про это
сказано, здесь — нет.

**Чем грозит.** Запись в DLQ с переданным `ctx` гарантированно провалится во время shutdown —
когда спасать и надо.

**Исправление.** Дописать в godoc; рекомендовать `context.WithoutCancel` внутри хука.

## У4 [УМЕРЕННО] `Start` после `Stop` возвращает «уже запущен» вместо «закрыт»

**Статус: открыто.** Проверено при закрытии волны 1 и намеренно не тронуто: `Start` взводит
`started` до проверки `stopping`, поэтому `Start` → `Stop` → `Start` по-прежнему даёт
`ErrConsumerStarted`. `ErrConsumerClosed` приходит только когда `Stop` случился раньше первого
`Start`.

**Где:** `consumer.go:321-341`, `errors.go:34-38`.

`started` — флаг «когда-либо стартовал». После `Stop` он остаётся `true` → повторный `Start`
падает на CAS с `ErrConsumerStarted` (`:324`). До проверки `stopping` (`:337`) доходит только если
`Stop` был раньше `Start`. Godoc `Start` честно пишет «не перезапускается» — расхождение осознано в
тексте, но не в коде.

Смежное: `AddHandler` на консьюмере, остановленном без запуска, **молча успешен** (`:298`
проверяет только `started`).

**Исправление.** Проверять `stopping` **до** CAS, возвращать `ErrConsumerClosed`; ту же проверку в
`AddHandler`. *Проверено вручную.*

## У5 [УМЕРЕННО] `*kerr.Error` вшит в публичный контракт ошибок

**Где:** `errors.go:22-26`, `doc.go:99-103` — godoc прямо предписывает `errors.As` до `*kerr.Error`.

Потребители получают жёсткую зависимость на `franz-go/pkg/kerr`. Смена клиента (один переход уже
пережит) сломает логику у каждого потребителя, и **компилятор не покажет** — `errors.As` просто
перестанет находить тип.

**Исправление.** Либо свой `DeliveryError{Topic, Code, Retriable, Err}`, либо явно зафиксировать в
документации, что `kerr` — часть контракта v2.

## Мелочи

* **Ни одной типизированной ошибки** — координаты сообщения только текстом: ошибка `SendMessage` не
  несёт `Topic`, ошибка финального коммита не несёт партиций.
* **Статтеры в именах:** `kafkax.KafkaProducer` / `NewKafkaConsumer` — «kafka» дважды. Хорошие
  имена заняты **секциями конфигурации**: `kafkax.Producer`, `kafkax.Consumer`. →
  `Producer`/`Consumer` для типов, `ProducerConfig`/`ConsumerConfig` для секций.
* **`ErrHandlerPanic` переиспользован для паники хука, причина теряется** — `consumer.go:682`:
  `fmt.Errorf("on message skipped: %w", ErrHandlerPanic)`, значение `recover()` не попадает
  (в `callHandler:770` есть `%v` от `r`). Godoc сентинела (`errors.go:28-32`) для этого пути неверен.
* ~~**Мёртвая ссылка в godoc ошибки**~~ — `errors.go:46`: «…который `SubscribeAll` передал бы в
  `ConsumeTopics`». `SubscribeAll` в репозитории нет (единственное вхождение — эта строка).
  **Закрыто волной 1:** godoc `ErrEmptyTopic` теперь называет `AddHandler` и `Start`.
* **Пять разных стилей префикса операции:** `invalid producer config:` (`producer.go:89`),
  `new_kafka_consumer:` (`consumer.go:252`, snake_case!), `start:` (`:322`),
  `send message:` (`producer.go:199`), `add handler:` (`consumer.go:288`).
* **Рассинхрон словаря:** `PublishRequest` / `IncomingMessage` / `SendMessage` — три слова на одну
  сущность.
* **Проверка длины ключа дублируется** вместо вызова `ValidateKeyLength` — `middleware.go:61-64` vs
  `encoding/key.go:116-127`. См. [08-style-docs.md](08-style-docs.md) У4.
* `config.go:518` — единственная ошибка валидации без `got %v`.
* `config.go:322-522` — ошибки называют поле yaml-путём; для `Config`, собранного в Go, нужен
  Go-путь.
* `consumer.go:29-34` — у `IncomingMessage` задокументирован только `Timestamp`;
  `Offset`/`Partition`/`Key` — нет.
* `producer.go:353` — число записей внутри текста ошибки высококардинально для группировки в APM.

## Проверено и в порядке

* **Владение памятью у продюсера:** `SendMessage` отдаёт `Key`/`Value` без копии
  (`producer.go:214-219`) — безопасно: `ProduceSync` ждёт промисы, промис срабатывает после того,
  как franz-go запись отпустил.
* Компайл-тайм проверки интерфейсов: `producer.go:82`, `consumer.go:83`.
* Агрегация валидации через `errors.Join`; тексты почти везде с полем, ожиданием и полученным
  значением.
* Двойной `%w` в `produceError:273` — корректно.
* `ErrHandlerPanic` проходит `errors.Is` в `cause` у `OnMessageSkipped`.
* `Headers.Get` — префикс оправдан прецедентом `http.Header.Get`.
* Нулевые значения `Headers`, `IncomingMessage`, `PublishRequest`, `SASL`, `TLS` — рабочие.
* Утечки внутренних типов в сигнатуры нет. Чужие типы в API — только `kgo.Opt` и `*tls.Config`,
  оба задокументированы.
* Пакет `encoding` действительно листовой.
