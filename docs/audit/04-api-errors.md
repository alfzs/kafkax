# 04. Ошибки и контракт API

**Статус:** 🟢 закрыто — 12 из 12
**Источник:** аудит пакета kafkax, 2026-07-29
**Зависит от:** 06-tests, 08-style-docs

## Контекст

Ошибки пакета делятся на две неравные части: там, где сентинелы есть, контракт работает, — а на
двух путях, где потребитель **обязан** среагировать (недослитый буфер продюсера и проваленный
финальный коммит), различить исход можно было только через `strings.Contains`. Рядом — `Config`
без годного нулевого значения и без `DefaultConfig()`, документированный разбор списка ошибок
валидации, ломающийся ровно в конструкторе, и контракт владения памятью `IncomingMessage`,
который не соответствует коду и внутренне противоречив.

Волной 2 закрыты RF-API-01, RF-API-02, RF-API-03, RF-API-04 — сентинелы завершения и настройки,
`DefaultConfig()`. Волной 1 не тронуто ничего, кроме мёртвой ссылки `SubscribeAll` в RF-API-12
(она же [08](08-style-docs.md) RF-DOCS-08). Волной 4 закрыты RF-API-05 — RF-API-11: контракт
владения буфером, типизированные части ключа, причина во всех исходах `produceError`, контракт
вызова `OnMessageSkipped`, тип `PanicSite`, три состояния жизненного цикла консьюмера и
собственный `DeliveryError` вместо `*kerr.Error` в контракте. Открытым остался только остаток
RF-API-12. Сводка — в [README.md](README.md).

## Задачи

### RF-API-01 · P1 · Ошибки завершения неклассифицируемы

**Статус:** 🟢 закрыто волной 2
**Прежний ID:** С1
**Где:** `producer.go:339`, `producer.go:353`, `consumer.go:994`.

**Проблема**

`"flush budget exhausted"`, `"flushing %d buffered records"`, `"committing marked offsets"` не
привязаны к сентинелам. В `errors.go` нет ни `ErrFlushIncomplete`, ни `ErrCommitFailed`.

**Чем грозит.** Это ровно те два случая, где потребитель **обязан** среагировать (алерт, повтор,
отказ от завершения) — а различить их можно только через `strings.Contains`. `defer
producer.Close()` теряет сообщения молча, след только WARN в логе.

**Решение**

`ErrFlushIncomplete`, `ErrCommitFailed`; при желании — типизированная
`*FlushError{Remaining int64}`.

Оба сентинела заведены в `errors.go` (`:87` и `:95`). Обе ветки `flush` возвращают
`ErrFlushIncomplete` — исчерпанный бюджет (`producer.go:378`) и таймаут с остатком в буфере
(`:393`); финальный коммит в `shutdown` — `fmt.Errorf("%w: %w", ErrCommitFailed, commitErr)`
(`consumer.go:1365`), то есть с сохранённой причиной.

Типизированную `*FlushError` заводить не стали: единственное её поле — число оставшихся записей,
которое уже есть и в тексте, и в записи WARN, а публичный тип пришлось бы поддерживать вечно ради
величины, по которой не принимают решений. Само число из текста ошибки не убрано, хотя для
группировки в APM оно высококардинально (см. RF-API-12).

**Критерий приёмки**

- [x] `TestProducerCloseBoundedByGracefulTimeout`: `Close` на недоступном брокере возвращает
      ошибку, опознаваемую через `errors.Is(err, ErrFlushIncomplete)`
- [x] `TestStopReportsFailedFinalCommit`: кластер гасится после обработки, но до `Stop`;
      `Stop` возвращает `ErrCommitFailed`, и причина развёрнута рядом с сентинелом
- [x] `TestSentinelsAreDistinct` и `TestSentinelsSurviveWrapping` покрывают оба новых сентинела
- [x] Второй тест закрывает и часть [06](06-tests.md) RF-TEST-02

**Риски:** сентинелы — часть публичного контракта, переименование или удаление ломает потребителей
молча (`errors.Is` просто перестанет находить). Откат правки возвращает `strings.Contains` как
единственный способ различить два исхода завершения.

### RF-API-02 · P1 · Повторная регистрация обработчика — без сентинела

**Статус:** 🟢 закрыто волной 2
**Прежний ID:** С2
**Где:** `consumer.go:306` — единственная ошибка `AddHandler` без сентинела (у трёх соседних он
есть).

**Проблема**

`consumer_test.go:547` уже проверяет `strings.Contains(err.Error(), "already registered")` — тест
зафиксировал строку как контракт, хотя `errors.go:5-6` объявляет текст **не** частью контракта.

*Проверено вручную.*

**Критерий приёмки**

- [x] `TestAddHandlerContract` (`consumer_test.go:552`) проверяет
      `errors.Is(err, ErrDuplicateHandler)`, а не подстроку
- [x] `strings.Contains(err.Error(), "already registered")` в тестах не встречается
- [x] Текст ошибки называет топик (`%q`), сентинел развёрнут через `%w`

**Риски:** нет. Чистое добавление сентинела; текст ошибки контрактом не был и не стал.

### RF-API-03 · P1 · Ошибки валидации непроверяемы; документированный разбор списка ломается в конструкторе

**Статус:** 🟢 закрыто волной 2
**Прежний ID:** С3
**Где:** `config.go:301-303`, `producer.go:89`, `consumer.go:255`.

**Проблема**

1. ~25 ошибок валидации без общего сентинела — `errors.Is(err, ErrInvalidConfig)` невозможен.
2. Godoc `Validate` обещает разворот через `errors.Unwrap() []error`. Конструкторы оборачивают
   joined-ошибку **ещё раз** (`fmt.Errorf("invalid producer config: %w", err)`) — у результата
   `Unwrap() error`, а не `[]error`. **Документированный приём на ошибке `NewKafkaProducer` не
   работает.**

**Решение**

Аудит предлагал `ErrInvalidConfig` + `errors.Join(append([]error{ErrInvalidConfig}, errs...)...)`;
в конструкторах не оборачивать повторно. **Закрыто волной 2, но не предложенным способом.**

Подмешивать сентинел в `errors.Join` нельзя: тогда он вылезает первым элементом `Unwrap() []error`,
и код, печатающий список претензий пользователю, начинает его строкой «invalid configuration».
Вместо этого заведён тип-агрегат `configError{subject, errs}` (`config.go:396`) с `Unwrap() []error`
(`:418` — только претензии к полям) и `Is(target) bool` (`:424` — отвечает `true` на
`ErrInvalidConfig`). Конструкторы отдают его как есть — обёртка через `fmt.Errorf` подменила бы
`Unwrap() []error` на `Unwrap() error`. Сам сентинел объявлен в `errors.go:104`.

**Критерий приёмки**

- [x] `TestValidationErrorsCarryInvalidConfigSentinel` проверяет обе стороны на всех трёх входах
      (`Validate`, `NewKafkaProducer`, `NewKafkaConsumer`): сентинел опознаётся через `errors.Is`,
      список разворачивается через `Unwrap() []error` и содержит ≥2 претензии
- [x] тот же тест: сентинела **нет** ни в одном элементе списка — иначе перечень полей начинался
      бы строкой «invalid configuration»
- [x] `TestValidConfigProducesNoError` закрывает ловушку nil-указателя в интерфейсе ошибки:
      `newConfigError("config", nil) == nil`; без неё ни один валидный конфиг не прошёл бы
      конструктор

**Риски:** `configError` неэкспортирован — потребитель работает с ним только через `errors.Is` и
`errors.Unwrap() []error`, и это единственный поддерживаемый способ. Любая обёртка результата через
`fmt.Errorf` в конструкторах снова сломает документированный разбор списка: `Unwrap() []error`
превратится в `Unwrap() error`.

### RF-API-04 · P1 · У `Config` нет годного нулевого значения и способа получить дефолты из кода

**Статус:** 🟢 закрыто волной 2
**Прежний ID:** С4
**Где:** `config.go:48-292`; `DefaultConfig` в пакете отсутствует.

**Проблема**

Все дефолты живут только в тегах `env-default` и материализуются лишь через `cleanenv`. `Config`,
собранный литералом в Go — полностью поддерживаемый путь, — даёт ~15 ошибок валидации.

**Чем грозит.** Тесты потребителя и любая программная конфигурация обязаны знать все 41 значение
по умолчанию наизусть.

**Решение**

`func DefaultConfig() Config` — чистое добавление, ломать ничего не нужно; плюс тест-сверка
возвращаемых значений с тегами `env-default`.

`DefaultConfig()` возвращает все 29 значений из тегов `env-default`. `Brokers`, `ClientID` и
`Consumer.Group` оставлены пустыми намеренно: умолчание у группы означало бы, что два забывших её
задать сервиса молча делят один assignment.

Значения продублированы в коде, а не вытащены рефлексией: разбор строк тега в рантайме стоил бы
парсинга на каждое поле и отдавал бы вызывающему ошибку разбора собственного тега. Плата за дубль —
`TestDefaultConfigMatchesStructTags`: обход по структуре сверяет обе стороны, поэтому поле с тегом,
но без строки в `DefaultConfig`, валит сборку тестов, а не продакшен потребителя. Проверка
двусторонняя — поле **без** тега обязано остаться нулевым.

**Критерий приёмки**

- [x] `TestDefaultConfigMatchesStructTags`: обход по структуре сверяет `DefaultConfig()` с тегами
      `env-default` в обе стороны — расхождение валит тесты
- [x] `TestDefaultConfigIsUsableAfterFillingRequiredFields`: `DefaultConfig()` плюс `Brokers`,
      `ClientID`, `Consumer.Group` проходит `Validate()` без ошибок
- [x] `TestDefaultConfigWithoutRequiredFieldsFailsValidation`: три намеренно пустых поля
      по-прежнему обязательны

**Риски:** дубль значений в коде и в тегах — источник расхождения, и держится он только тестом;
если `TestDefaultConfigMatchesStructTags` удалят, новое поле молча уедет с нулевым значением.
Само добавление обратной совместимости не ломает.

### RF-API-05 · P1 · Контракт владения памятью `IncomingMessage` не соответствует коду и внутренне противоречив

**Статус:** 🟢 закрыто волной 4
**Прежний ID:** С5
**Где:** `consumer.go:25-27` (godoc), `consumer.go:654` и `:686` (нарушение), `config.go:89-103`;
**плюс blockquote в README, раздел «Быстрый старт»**.

**Проблема**

Godoc: «`Key`, `Value`, `Headers` живут ровно столько, сколько длится вызов обработчика».

По исходникам franz-go v1.21.5 переиспользование буферов включается **только** через
`kgo.WithPools` (`kgo/source.go:1765-1779` — put-back лишь при зарегистрированном
`PoolDecompressBytes`; `Record.Recycle()` в `kgo/pools.go:122` — no-op без `r.Context`). kafkax
`WithPools` не вызывает → буферы обычные, GC-управляемые. Собственный код это подтверждает:
`dispatch` (`:464-478`) держит до `MessageQueueSize` батчей в канале.

**Противоречие внутри пакета:** `resolveFailure` передаёт тот же `msg` в `OnMessageSkipped`
**после** возврата из `ProcessMessage` (`:654` → `:686`) — библиотека по собственным правилам
отдаёт просроченные буферы.

Отдельно: `Config.ExtraOpts` позволяет протащить `kgo.WithPools`, после чего правило станет
правдой, а `Recycle()` kafkax не вызывает — пулинг выродится в отсутствие возврата памяти.

*Проверено вручную: `WithPools`/`Recycle` не вызываются в репозитории нигде.*

**Решение**

Привести godoc и README к коду: «срез разделяется с записью franz-go; пулинг не включён, но
мутировать нельзя — те же срезы уходят в повторы и в `OnMessageSkipped`». Продублировать в godoc
`OnMessageSkipped`.

Раздел «Владение памятью» в godoc `IncomingMessage` переписан целиком. `Key` и `Value` названы
срезами, разделяемыми с записью franz-go, а не копиями; чтение после возврата из обработчика
объявлено безопасным — но не как обещание на будущее, а как следствие: пулинг не включён, потому
что `kgo.WithPools` пакет не вызывает, и буферы живут как обычные объекты под управлением GC.

Запрет мутации назван отдельно и с причиной: тот же самый срез пакет отдаёт в каждую попытку
повтора и затем в `Config.OnMessageSkipped` — уже после возврата из `ProcessMessage`. Отсюда же
переформулировано и правило копирования: копировать нужно «чтобы изменить», а не «чтобы пережить
вызов». Прежний текст учил ровно обратному, и это единственное место, где ослабление обещания
могло бы кого-то подвести.

Из двух вариантов по `ExtraOpts` выбран первый: `kgo.WithPools` объявлен неподдерживаемым
(`config.go:80-83` и тот же абзац в godoc `IncomingMessage`). Вызов `Recycle()` отвергнут —
он сделал бы правдой ровно то утверждение, от которого правка уходит, и превратил бы чтение
буфера после возврата из обработчика в порчу данных.

Тот же текст продублирован в godoc `OnMessageSkipped` (раздел «Владение памятью») и в blockquote
README «Быстрый старт».

Обещание снято тестом, а не «прочитано по коду»: `consumer_ownership_test.go`
`TestMessageBuffersOutliveHandlerAndAreShared` сравнивает адреса первого байта `Value` в трёх
точках — два вызова обработчика (исходный и повтор) и хук skip — и заодно проверяет, что
содержимое в хуке цело. Сравниваются именно адреса: два разных буфера с одинаковыми байтами по
значению неотличимы, а вопрос стоит про разделяемую память.

**Критерий приёмки**

- [x] Godoc `IncomingMessage` (`consumer.go:25-27`) не утверждает, что срезы живут только на время
      вызова обработчика
- [x] Тот же текст продублирован в godoc `OnMessageSkipped` (`config.go:89-103`) и в blockquote
      README «Быстрый старт»
- [x] Ограничение «мутировать нельзя» названо явно, с причиной: те же срезы уходят в повторы и
      в `OnMessageSkipped`
- [x] Поведение `ExtraOpts` + `kgo.WithPools` либо задокументировано как неподдерживаемое, либо
      закрыто вызовом `Recycle()` — выбран первый вариант

**Риски:** правка документации меняет обещание в сторону ослабления — потребители, копировавшие
`Value` из-за прежнего godoc, ничего не сломают. Обратное неверно: если оставить как есть, кто-то
положится на буквальное «живут ровно столько» и мутирует срез.

### RF-API-06 · P1 · `encoding.EncodeKey(parts ...any)` — API, который сам документирует свою ловушку

**Статус:** 🟢 закрыто волной 4
**Прежний ID:** С6
**Где:** `encoding/key.go:35-74`, godoc `:81-88`.

**Проблема**

Ключ из `...any` с рантайм-свитчем по четырём типам. Godoc `MatchKey` прямым текстом описывает
отказ: «опечатка в типе (`int` вместо `int64`)» — и лечится он паникой, а не системой типов.
`EncodeKey(42)` компилируется. Ошибки `EncodeKey` не привязаны к сентинелу.

**Решение**

Типизированный билдер `encoding.NewKey().UUID(x).Str(y).Int64(z).Build()`; минимум —
`ErrUnsupportedKeyPart`.

**Закрыто волной 4, но не предложенным способом — взят максимальный вариант, а не билдер.**
`...any` заменён на непрозрачный тип `encoding.KeyPart`, значения которого собираются **только**
конструкторами `encoding.UUID`, `Str`, `Int64` и `Bool`. Рантайм-свитч по четырём типам исчез
вместе с самой возможностью ошибиться: `EncodeKey(42)` больше не компилируется, и godoc `MatchKey`
больше не документирует собственную ловушку — документировать нечего.

Fluent-билдер из формулировки задачи отвергнут: он аккумулирует байты, не зная заранее итогового
размера, то есть несовместим с одной аллокацией на ключ, которую даёт RF-PERF-05
([07-performance.md](07-performance.md)). Дженерик-вариант отвергнут отдельно и по другой
причине: variadic-дженерик требует одного типа на все аргументы, а композитный ключ разнороден по
определению. Обоснование записано не только здесь, но и в godoc `KeyPart` — там, где его увидит
следующий, кому эта мысль придёт.

Вместо `ErrUnsupportedKeyPart` заведены два сентинела, потому что осталось два разных отказа, и
ни один из них уже не про «неподдерживаемый тип»: `ErrInvalidKeyPart` — нулевое значение
`KeyPart` (из `make([]KeyPart, n)` или незаполненного поля структуры), `ErrKeyPartTooLong` —
строка длиннее `math.MaxUint32`.

Тесты на прежний рантайм-отказ переписаны под новый контракт и переименованы вслед за ним:
`TestEncodeKey_InvalidPart`, `TestMatchKey_InvalidPartPanics`, `TestNewKey_InvalidPart`,
`TestValidateKeyLength_EncodeError`, `TestKeyPart_AppendToInvalidWritesNothing`.

**Неточность аудита.** Формулировка задачи называла минимальным вариантом сентинел
`ErrUnsupportedKeyPart` — то есть предполагала, что «неподдерживаемый тип части» останется
рантайм-состоянием. После перехода на `KeyPart` этого состояния не существует: непредставимой
части нет, есть незаполненная. Имя сентинела из аудита в код не попало намеренно, оно описывало бы
не тот отказ.

**Критерий приёмки**

- [x] `encoding.NewKey().Int(42)` не компилируется (либо, в минимальном варианте,
      `errors.Is(err, ErrUnsupportedKeyPart)` работает на `EncodeKey(42)`) — взята первая ветка:
      не компилируется ни `Int(42)`, ни `EncodeKey(42)`
- [x] `TestEncodeKey_UnsupportedType` и `TestMatchKey_UnsupportedTypePanics` переписаны на новый
      контракт и проходят — под именами `TestEncodeKey_InvalidPart` и
      `TestMatchKey_InvalidPartPanics`
- [x] Байтовое представление ключа не меняется: `TestEncodeKey_Deterministic`,
      `TestEncodeKey_StringLengthBigEndian`, `TestEncodeKey_PartOrderMatters` — ожидаемые байты
      в них не тронуты; правка коснулась только вызовов, где части обёрнуты конструкторами

**Риски:** билдер — новый публичный API в `encoding`; старый `EncodeKey` придётся либо оставить,
либо ломать потребителей. Байты ключа менять нельзя ни при каком варианте — от них зависит
партиционирование уже отправленных сообщений.

### RF-API-07 · P2 · `produceError` теряет причину у двух из четырёх исходов

**Статус:** 🟢 закрыто волной 4
**Прежний ID:** У1
**Где:** `producer.go:252-275`. Ветки `ErrDeliveryTimeout` и `ErrProducerClosed` возвращают голый
сентинел. Четыре разных формы у одной функции; `SendMessage` добавляет пятую.

**Проблема**

Не различить «наш `context.DeadlineExceeded`» от «`kgo.ErrRecordTimeout`» — разные диагнозы.

**Решение**

`fmt.Errorf("send message: %w: %w", ErrDeliveryTimeout, err)` во всех ветках.

Двойной `%w` теперь стоит во всех ветках, где сентинел вообще есть: `ErrDeliveryTimeout`,
`ErrProducerClosed` и `ErrDeliveryFailed`. Разделение труда сформулировано в godoc функции:
сентинел отвечает на вопрос «повторять ли», причина — на вопрос «что именно случилось». Без
причины наш `context.DeadlineExceeded` и `kgo.ErrRecordTimeout` неразличимы, хотя означают разное:
первое — мал бюджет вызова, второе — клиент не смог дослать запись.

Исключение одно и оно намеренное: ветка `context.Canceled` остаётся без сентинела
(`fmt.Errorf("send message: %w", err)`). Отмена — решение вызывающего, а не отказ Kafka, и
подменять её сентинелом доставки значило бы сообщать вызывающему о проблеме там, где он сам её и
создал. Причина здесь и есть вся ошибка, добавлять к ней нечего. Префикс называет операцию, а не
причину: `ctx.Done()` срабатывает и на отмене, и на дедлайне, поэтому «context canceled: context
deadline exceeded» противоречило бы само себе.

Тесты: `TestProduceErrorMapping` получил поле `wantCause` и проверяет обе стороны на шести входах;
`TestProduceErrorSeparatesTimeoutCauses` — ровно тот случай, ради которого задача заведена:
один сентинел, две причины, и ни одна не опознаётся как другая;
`TestProduceErrorPropagatesCancellation` стережёт ветку без сентинела — отмена не должна
опознаваться ни одним сентинелом пакета;
`producer_test.go` `TestProducerSendMessageDeliveryTimeout` проверяет то же на живом продюсере.

**Критерий приёмки**

- [x] `TestProduceErrorMapping` проверяет, что во всех ветках **с сентинелом** причина развёрнута
      рядом с ним (`errors.Is` на оба); ветка `context.Canceled` сентинела не несёт намеренно и
      покрыта отдельно — `TestProduceErrorPropagatesCancellation`
- [x] `TestProducerSendMessageDeliveryTimeout` различает `context.DeadlineExceeded` и
      `kgo.ErrRecordTimeout` по развёрнутой причине
- [x] `TestProduceErrorKeepsBrokerError` и `TestProduceErrorUnwrapsWrappedBrokerError` зелёные —
      но не «без изменений»: первый переписан на `DeliveryError` в той же волне по RF-API-11

**Риски:** текст ошибки меняется — тесты потребителей, сверяющие строку, сломаются, но текст
контрактом не объявлен (`errors.go:5-6`). Сентинелы остаются на месте, `errors.Is` продолжает
работать.

### RF-API-08 · P2 · Контракт вызова `OnMessageSkipped` не документирован

**Статус:** 🟢 закрыто волной 4
**Прежний ID:** У2
**Где:** `config.go:89-103`.

**Проблема**

Godoc объясняет семантику возврата, но молчит о вызове. По коду (`consumer.go:637-687`): вызывается
синхронно из горутины партиционного воркера; `ctx` = `msgCtx`, отменяется при жёсткой остановке и
по таймауту `awaitWorkers` (`:924`); блокировка держит партицию и съедает `RebalanceTimeout`;
паника перехватывается и трактуется как «не забрал». У `OnPanic` (`config.go:85-86`) про это
сказано, здесь — нет.

**Чем грозит.** Запись в DLQ с переданным `ctx` гарантированно провалится во время shutdown —
когда спасать и надо.

**Решение**

Дописать в godoc; рекомендовать `context.WithoutCancel` внутри хука.

Godoc `OnMessageSkipped` разбит на разделы. «Как вызывается»: синхронно, из горутины
партиционного воркера; на всё время вызова партиция стоит, а пришедший в этот момент ребаланс
ждёт возврата из хука; хук, живущий дольше `Consumer.RebalanceTimeout`, стоит группе исключения
участника — то есть `onLost` вместо управляемого отзыва партиций. Там же — трактовка паники как
«не забрал», с причиной: считать упавший хук забравшим значило бы терять сообщение ровно тогда,
когда его пытались спасти.

«Контекст»: `ctx` отменяется при жёсткой остановке и по истечении бюджета ожидания воркеров, то
есть ровно во время shutdown, когда спасать сообщение и надо, — запись в DLQ этим контекстом в
такой момент провалится гарантированно. Рекомендация дана готовым сниппетом
(`context.WithTimeout(context.WithoutCancel(ctx), …)`) и с отдельной оговоркой, что спан и
trace-контекст при этом сохраняются: `WithoutCancel` снимает только отмену и дедлайн, и это как
раз то, чего от него ждут не все.

Третьим разделом добавлено «Владение памятью» — ссылка на `IncomingMessage` из RF-API-05: `msg.Key`
и `msg.Value` здесь те же самые срезы, что видел обработчик.

Своего теста у задачи нет и он не нужен: поведение не менялось ни на байт, менялся только текст,
описывающий его. Всё перечисленное уже покрыто тестами хука, заведёнными раньше.

**Критерий приёмки**

- [x] Godoc `OnMessageSkipped` называет: синхронный вызов из горутины партиционного воркера,
      источник `ctx`, влияние блокировки на `RebalanceTimeout`, трактовку паники как «не забрал»
- [x] Рекомендация `context.WithoutCancel` присутствует с объяснением: во время shutdown
      переданный `ctx` уже отменён
- [x] Поведение подтверждено существующими тестами: `TestSkipHookNilCommitsAndContinues`,
      `TestSkipHookErrorPausesPartition`, `TestSkipHookPanicPausesPartition`

**Риски:** только документация, кода не касается.

### RF-API-10 · P2 · `Start` после `Stop` возвращает «уже запущен» вместо «закрыт»

**Статус:** 🟢 закрыто волной 4
**Прежний ID:** У4
**Где:** `consumer.go:321-341`, `errors.go:34-38`.

**Проблема**

Проверено при закрытии волны 1 и намеренно не тронуто: `Start` взводит `started` до проверки
`stopping`, поэтому `Start` → `Stop` → `Start` по-прежнему даёт `ErrConsumerStarted`.
`ErrConsumerClosed` приходит только когда `Stop` случился раньше первого `Start`.

`started` — флаг «когда-либо стартовал». После `Stop` он остаётся `true` → повторный `Start`
падает на CAS с `ErrConsumerStarted` (`:324`). До проверки `stopping` (`:337`) доходит только если
`Stop` был раньше `Start`. Godoc `Start` честно пишет «не перезапускается» — расхождение осознано в
тексте, но не в коде.

Смежное: `AddHandler` на консьюмере, остановленном без запуска, **молча успешен** (`:298`
проверяет только `started`).

*Проверено вручную.*

**Решение**

Проверять `stopping` **до** CAS, возвращать `ErrConsumerClosed`; ту же проверку в `AddHandler`.

**Закрыто волной 4, но не двумя проверками, а переходом на состояние.** Два независимых флага
`started atomic.Bool` и `stopping atomic.Bool` описывали три состояния четырьмя комбинациями, из
которых одна («не стартовал, но остановлен») означала то же, что и другая, а порядок их взведения
и был дефектом. Вместо ещё одной проверки заведён `state atomic.Int32` поверх `consumerState` с
тремя значениями — `consumerIdle`, `consumerRunning`, `consumerClosed` — и методом
`lifecycleErr()`, который один отвечает на вопрос «почему операция, разрешённая только до старта,
запрещена сейчас». `Start` делает CAS `idle → running` и на отказе спрашивает состояние: закрыт —
`ErrConsumerClosed`, запущен — `ErrConsumerStarted`.

Две детали, без которых правка была бы неверной. Первая: откат неуспешного старта — CAS
`running → idle` (`abortStart`), а не `Store(idle)`; безусловная запись воскресила бы консьюмера,
который между началом старта и его провалом успел получить `Stop`. Вторая: `shutdown` пишет
`consumerClosed` **до** захвата `c.mu` — порядок, введённый волной 1 против «осиротевшего»
клиента при SIGTERM во время старта, и он сохранён.

**Неточность аудита №1: настоящая дыра была шире формулировки.** Задача называет `AddHandler` на
остановленном консьюмере «смежным», но именно он был опаснее: он возвращал `nil`, то есть врал
успешно. `Start` хотя бы ошибался — говорил «уже запущен» вместо «закрыт», и вызывающий видел
отказ. `AddHandler` же сообщал об успехе регистрации, которой не произошло и произойти уже не
могло. Это молчаливый отказ, и закрыт он вместе с исходной претензией, одним состоянием на обоих
путях.

**Неточность аудита №2: к продюсеру задача не применима.** Формулировка упоминает продюсер
наравне с консьюмером, но у `KafkaProducer` нет `Start`: `NewKafkaProducer` отдаёт готовый
объект, состояний ровно два — «работает» и «закрыт», — и `SendMessage` после `Close` уже
возвращал `ErrProducerClosed` до всякой правки. Различать «не запущен» и «закрыт» там нечего,
и ничего в продюсере по этой задаче не менялось.

Тесты: `consumer_test.go` `TestStartContract` получил случай «Start после полного цикла
Start-Stop» — он же проверяет, что `ErrConsumerStarted` в этом исходе **не** возвращается, потому
что прежнее поведение предлагало ждать освобождения, которого не будет; `TestAddHandlerContract` —
случай «после Stop».

**Критерий приёмки**

- [x] `Start` → `Stop` → `Start` возвращает `ErrConsumerClosed`, а не `ErrConsumerStarted`
- [x] `AddHandler` на остановленном консьюмере возвращает `ErrConsumerClosed`, а не успех
- [x] `TestStartContract` и `TestAddHandlerContract` дополнены обоими случаями
- [x] `TestStopWithoutStart` продолжает проходить: `Stop` до `Start` по-прежнему не ошибка

**Риски:** меняется наблюдаемое поведение двух публичных методов — код, различающий
`ErrConsumerStarted` и `ErrConsumerClosed`, получит другую ветку. `AddHandler`, который сейчас
молча успешен, начнёт возвращать ошибку: потребитель, регистрирующий обработчики после `Stop`,
это заметит.

### RF-API-11 · P2 · `*kerr.Error` вшит в публичный контракт ошибок

**Статус:** 🟢 закрыто волной 4
**Прежний ID:** У5
**Где:** `errors.go:22-26`, `doc.go:99-103` — godoc прямо предписывает `errors.As` до `*kerr.Error`.

**Проблема**

Потребители получают жёсткую зависимость на `franz-go/pkg/kerr`. Смена клиента (один переход уже
пережит) сломает логику у каждого потребителя, и **компилятор не покажет** — `errors.As` просто
перестанет находить тип.

**Решение**

Либо свой `DeliveryError{Topic, Code, Retriable, Err}`, либо явно зафиксировать в документации,
что `kerr` — часть контракта v2.

Выбран первый вариант. `errors.go` заводит `DeliveryError{Topic, Code, Name, Description,
Retriable, Err}` с `Unwrap` и `Is`. Против предложенного набора полей добавлены `Name` и
`Description`: без них потребитель, увидев `Code`, всё равно пошёл бы за расшифровкой в `kerr` —
то есть зависимость никуда бы не делась, только стала бы неявной.

Смысл `Code == 0` описан отдельно, потому что он неочевиден: нуля в протоколе нет, ноль означает
«кода не было вовсе» — отказ случился до ответа брокера (сеть, TLS, разрешение имени). `Retriable`
при этом всегда `false`, и godoc говорит прямо, что это «клиент не сказал», а не «повторять
бессмысленно».

`newDeliveryError` — единственная точка во всём непроверочном коде пакета, где вообще упоминается
`*kerr.Error` (проверено грепом: `errors.go:181`, других вхождений вне тестов нет). Это и есть
результат задачи: при следующей смене клиента правится одна функция, а не код каждого
потребителя. Сам `*kerr.Error` остаётся достижим через `Unwrap` — для отладки и чтобы `errors.Is`
продолжал находить сентинелы franz-go в цепочке, — но из контракта убран явным утверждением.

Метод `Is` связывает тип с сентинелом: `errors.Is(err, ErrDeliveryFailed)` отвечает `true` и на
`*DeliveryError`, полученной без обёртки, — иначе разбор зависел бы от того, обернул ли вызывающий
код ошибку, а это ровно та хрупкость, от которой уходит вся категория.

Тесты: `errors_test.go` `TestProduceErrorKeepsBrokerError` (переписан на `DeliveryError`),
`TestDeliveryErrorWithoutBrokerCode` (отказ без кода протокола: `Code == 0`, `Retriable == false`),
`TestDeliveryErrorIsSentinelWithoutWrapping`, `producer_test.go` `TestProducerSendMessageBrokerError`.

**Критерий приёмки**

- [x] Выбран один из двух вариантов и записан в `doc.go` явным утверждением, а не умолчанием —
      раздел «Разбор ошибок и типы franz-go»
- [x] Заведён `DeliveryError` — `TestProduceErrorKeepsBrokerError` и
      `TestProduceErrorUnwrapsWrappedBrokerError` переписаны на него, а `*kerr.Error` остаётся
      достижим через `errors.As` в цепочке
- [x] Ветка «зафиксировать `kerr` в контракте» отвергнута, и это сказано утверждением, а не
      умолчанием: `doc.go` и README называют типы franz-go **не** частью публичного контракта v2

**Риски:** первый вариант — новый публичный тип, который придётся поддерживать при любой смене
клиента; второй — сознательная фиксация чужого типа в контракте, то есть блокировка смены клиента
без мажорной версии.

* `producer.go:353` — число записей внутри текста ошибки высококардинально для группировки в APM.

**Решение**

Мёртвая ссылка закрыта волной 1: godoc `ErrEmptyTopic` называет `AddHandler` и `Start` вместо
несуществующего `SubscribeAll`.

Остальное закрыто волной 8. По пунктам, где решение отличается от предложенного находкой:

**Префиксы.** Выбран герундий в нижнем регистре («sending message:», «creating consumer:»).
Он и так был самым частым из пяти сосуществовавших стилей и совпадает с общепринятым в Go.
Альтернатива «префикс = имя экспортированного метода» отвергнута: у половины мест, где ошибка
рождается (`caCertPool`, `compressionCodec`, `producerOpts`, `registerInstrument`),
экспортированного метода над ними нет вовсе, и правило пришлось бы делить надвое. Цена названа
прямо в тексте правила: grep по `SendMessage` из лога больше не попадает в код с первого раза.
Правило записано отдельным блоком в шапке `errors.go` — это файл, который открывают, добавляя
ошибку, — и не как godoc, чтобы не протекать в публичную документацию.

**Исключение из правила одно и оно обязательное:** агрегат валидации. Обёртка через `fmt.Errorf`
подменила бы у него `Unwrap() []error` на `Unwrap() error`, то есть «привести к общему стилю»
здесь означало бы сломать документированный разбор претензий, а не текст.

**yaml-путь против Go-пути.** Основным стал Go-путь, env-переменная идёт следом в скобках:
`Consumer.MaxBytes (env KAFKAX_CONSUMER_MAX_BYTES) must be positive, got 0`. Имя переменной не
берётся из таблицы, а выводится из Go-пути — таблица разошлась бы с тегами молча; соответствие
сторожит тест, обходящий `Config` рефлексией.

**Число записей в тексте ошибки продюсера — прежнее решение отменено.** Обоснование RF-API-01
(«число и так есть в записи WARN») перестало быть верным: волной 6 запись в лог убрана, и текст
стал единственным носителем величины. Получалось, что пакет объявляет текст не-контрактом и
одновременно вынуждает его парсить ради числа, по которому строят алерт. Заведён `*FlushError`
с полем `Remaining`, текст числа больше не содержит — два стабильных исхода вместо шаблона на
каждое значение счётчика.

**Переименование типов** (`Producer`/`Consumer` вместо `KafkaProducer`/`KafkaConsumer`, секции
конфигурации — в `ProducerConfig`/`ConsumerConfig`) выполнено `gopls`, а не текстовой заменой:
имя типа секции и имя поля `Config` текстом неразличимы. Имена полей `Config.Producer` и
`Config.Consumer` сохранены — переименовать и их значило бы получить
`cfg.ProducerConfig.MaxRetries`, длиннее и хуже читаемое.

**Типизированные ошибки, что сознательно НЕ сделано.** `Topic` в остальных ошибках `SendMessage`
— вызывающий держит `req.Topic` в руке на месте вызова. Типизированные ошибки полей конфигурации
— реакция сервиса на невалидный конфиг ровно одна: напечатать и не подняться; публичный тип на
25 сообщений пришлось бы поддерживать вечно ради решения, которого никто не принимает.

**Критерий приёмки**

- [x] `SubscribeAll` не встречается в репозитории ни разу; godoc `ErrEmptyTopic` называет
      `AddHandler` и `Start`
- [x] Все префиксы операций — в одном стиле, `new_kafka_consumer:` не встречается. Правило
      записано в шапке `errors.go`, и его стережёт `TestErrorPrefixesFollowGerundRule`: пять
      стилей разъехались именно потому, что каждый новый вызов писался по образцу соседа, и
      записанное без проверки правило повторило бы это с нуля. Единственное исключение
      закреплено отдельно — `TestConfigAggregateStaysUnprefixed` проверяет не отсутствие
      префикса, а то, ради чего его нет: разворот `Unwrap() []error`
- [x] `callSkipHook` доносит значение `recover()` в текст ошибки, как `callHandler`; godoc
      `ErrHandlerPanic` действительно был неверен — обещал только `ProcessMessage` — и теперь
      называет оба пути
- [x] Заикание в именах убрано: `Producer`/`Consumer` для клиентов,
      `ProducerConfig`/`ConsumerConfig` для секций; таблица замен — в README
- [x] `Offset`, `Partition` и `Key` у `IncomingMessage` задокументированы
- [x] Дубля проверки длины нет — закрыто волной 4 в [08](08-style-docs.md) RF-DOCS-07: правило
      живёт в `encoding.Key.ValidateLength`, её зовут и middleware, и `encoding.ValidateKeyLength`
- [x] Каждая ошибка валидации содержит значение и Go-путь поля с env-переменной в скобках

**Риски:** тексты ошибок изменились массово; контрактом они не объявлены, но тесты
потребителей, сверяющие строки, сломаются. Переименование типов — ломающее изменение публичного
API; ограничение снято владельцем репозитория (потребители в рефакторинге и будут адаптированы),
миграция сводится к таблице замен, компилятор укажет каждое место.

## Что осознанно не делаем

- **Не подмешиваем `ErrInvalidConfig` в `errors.Join`** — предложенный аудитом способ отвергнут:
  сентинел вылезал бы первым элементом `Unwrap() []error`, и код, печатающий список претензий
  пользователю, начинал бы его строкой «invalid configuration». Вместо него — тип-агрегат
  `configError` с `Is(target)` (RF-API-03).
- **Не оборачиваем результат валидации в конструкторах через `fmt.Errorf`** — обёртка подменила бы
  `Unwrap() []error` на `Unwrap() error`, то есть сломала бы документированный разбор списка ровно
  там, где он и был сломан до правки (RF-API-03).
- **Не заводим типизированную `*FlushError{Remaining int64}`** — единственное её поле уже есть и в
  тексте ошибки, и в записи WARN, а публичный тип пришлось бы поддерживать вечно ради величины, по
  которой не принимают решений (RF-API-01).
- **Не убираем число оставшихся записей из текста ошибки `flush`** — для группировки в APM оно
  высококардинально, но это единственное место, где число вообще доступно вызывающему
  (RF-API-01, RF-API-12).
- **Не вытаскиваем дефолты рефлексией из тегов `env-default`** — разбор строк тега в рантайме
  стоил бы парсинга на каждое поле и отдавал бы вызывающему ошибку разбора собственного тега;
  дубль в коде стережёт `TestDefaultConfigMatchesStructTags` (RF-API-04).
- **Не даём умолчания `Brokers`, `ClientID` и `Consumer.Group`** — умолчание у группы означало бы,
  что два забывших её задать сервиса молча делят один assignment (RF-API-04).
- **Не вызываем `Record.Recycle()` ради пулинга буферов** — это сделало бы правдой утверждение
  «срез живёт ровно столько, сколько длится вызов», от которого правка и уходит, и превратило бы
  чтение `Value` после возврата из обработчика в порчу данных. `kgo.WithPools` через `ExtraOpts`
  объявлен неподдерживаемым (RF-API-05).
- **Не делаем fluent-билдер ключа** — он аккумулирует байты, не зная итогового размера, то есть
  несовместим с одной аллокацией на ключ из [07](07-performance.md) RF-PERF-05. Дженерик отвергнут
  отдельно: variadic-дженерик требует одного типа на все аргументы, а ключ разнороден (RF-API-06).
- **Не заводим сентинел на «неподдерживаемый тип части»** — после перехода на `encoding.KeyPart`
  такого состояния не существует, отказ бывает только на нулевом значении части и на слишком
  длинной строке (RF-API-06).
- **Не даём сентинел ветке `context.Canceled` в `produceError`** — отмена это решение вызывающего,
  а не отказ Kafka; причина здесь и есть вся ошибка (RF-API-07).
- **Не фиксируем `franz-go/pkg/kerr` в публичном контракте v2** — вместо этого заведён
  `DeliveryError`, а зависимость на чужой тип сведена к одной функции `newDeliveryError`
  (RF-API-11).
