# 01. Конкурентность и жизненный цикл

**Статус:** 🟢 закрыто
**Источник:** аудит пакета kafkax, 2026-07-29
**Зависит от:** —

## Контекст

У остановки консьюмера не было единого владельца: отмена `ctx`, `Stop` и цикл опроса завершали
экземпляр каждый по-своему, и три критические находки ниже — **одна корневая причина**, а не три
независимых дефекта; правильнее было чинить их одним рефакторингом, а не по отдельности. Разбор
оставлен как есть — он объясняет, почему остановка устроена так, как устроена. Номера строк
относятся к дореформенному коду. Сводка — в [README.md](README.md).

## Задачи

### RF-CONC-01 · P0 · Отмена `ctx`, переданного в `Start`, не останавливает консьюмер

**Статус:** 🟢 закрыто волной 1
**Прежний ID:** К1
**Где:** `consumer.go:382-389` (`watchContext`), `:410-442` (`runPollLoop`), `:529` (тело воркера).

**Проблема**

`watchContext` на отмену делает ровно одно — `c.lifeCancel()`. Дальше:

* `runPollLoop` выходит по `context.Canceled`, но **оба ранних `return` минуют
  `client.AllowRebalance()`** (`consumer.go:440` — единственное вхождение в файле);
* `kgo.Client` **не закрывается**: продолжает heartbeat, остаётся членом группы;
* воркеры висят на `for batch := range w.records` — канал закрывает только `w.stop()`
  (`consumer.go:137-139`), которого никто не вызовет; `ctx.Err()` проверяется **только внутри
  уже полученного батча** (`:534`), простаивающий воркер отмены не видит;
* декремент `workersActive` живёт в defer горутины (`:515`) → не выполняется никогда;
* отмеченные оффсеты не коммитятся.

Отдельно: **godoc `Start` прямо называет отмену `ctx` эквивалентом `Stop`.** Сейчас это неправда.

**Чем грозит.** Экземпляр становится зомби: партиции за ним закреплены **навсегда** (не до
session timeout — heartbeat продолжается), гейт `BlockRebalanceOnPoll` зажат, координатор ждёт
этот экземпляр до `RebalanceTimeout` на **каждом** ребалансе, остальные участники простаивают.
Метрика показывает N живых воркеров до конца процесса.

*Проверено вручную: `watchContext`, оба `return` в `runPollLoop`, единственность `AllowRebalance`,
отсутствие закрытия канала где-либо кроме `stop()`.*

**Решение**

`watchContext` должен инициировать полное завершение (вызвать тот же путь, что `Stop`), а не
только `lifeCancel`. Независимо от этого: `defer client.AllowRebalance()` внутри тела итерации,
и чтение очереди воркера через
`select { case batch, ok := <-w.records: …; case <-ctx.Done(): return }`.

Сделано волной 1. `watchContext` инициирует полную остановку через `Stop`, а не голый
`lifeCancel`: отмена контекста обязана оставлять после себя закрытого клиента и закоммиченные
оффсеты. Итерация опроса вынесена в отдельную функцию `pollOnce` ровно ради `defer
client.AllowRebalance()` — в теле цикла есть два ранних выхода и возможная паника, которые его
миновали бы. Воркер читает очередь `select`'ом наравне с `<-ctx.Done()`.

**Критерий приёмки**

- [x] `TestStartContextCancelStopsConsumer`: после отмены контекста `Start` вызов `Stop`
      возвращает `nil`, а свежий консьюмер на той же группе получает только маркер — при
      `CommitInterval=1h`, то есть финальный коммит прошёл, а не тикер автокоммита
- [x] `AllowRebalance` вызывается на каждой итерации через `defer` в `pollOnce`; ранние выходы
      (`fetches.IsClientClosed()`, `context.Canceled`) и паника его не минуют
- [x] `runPartitionWorker` читает `w.records` в `select` с `<-ctx.Done()` — простаивающий воркер
      видит отмену
- [x] `go test -race ./...` проходит под goleak (`TestMain` в `leaks_test.go`,
      `IgnoreTopFunction` пуст) — ни `watchContext`, ни воркеры не переживают тест

**Риски:** откат превращает отмену контекста обратно в частичную остановку — зомби-экземпляр в
группе с живым heartbeat. Миграции и смены конфига не требует; godoc `Start` снова разошёлся бы
с поведением.

### RF-CONC-02 · P0 · TOCTOU между `Start` и `Stop`: созданный клиент остаётся без закрывающего

**Статус:** 🟢 закрыто волной 1
**Прежний ID:** К2
**Где:** `consumer.go:337-341` (проверка `stopping`), `:359` (`kgo.NewClient`), `:368-371`
(публикация под `c.mu`); `Stop` — `:946-962`.

**Проблема**

Проверка `c.stopping.Load()` и публикация `c.client` разнесены на 30 строк, между ними
сетевой вызов `kgo.NewClient`. `Stop`, попавший в это окно:

1. `CompareAndSwap(false, true)` проходит — `stopping` взведён **навсегда**;
2. под `c.mu` читает `c.client` — там ещё `nil`;
3. уходит по ранней ветке `if client == nil { c.lifeCancel(); return nil }`.

`Start` следом публикует уже созданный клиент. Любой последующий `Stop` — no-op на
`CompareAndSwap` с warn'ом «Consumer is already stopping».

**Чем грозит.** Клиент присоединился к группе, синхронизировал assignment, вошёл в heartbeat-цикл —
и закрыть его больше нечем. Субагент воспроизвёл: после возврата `Stop()` в логах
`joined, balancing group` → `synced assigned=…` → `beginning heartbeat loop`, клиент отвечает
на `Ping`. Типовой триггер — `Stop` по SIGTERM во время старта пода.

*Проверено вручную: порядок `:337` → `:359` → `:368-371` и ранняя ветка `Stop` — подтверждаются.*

**Решение**

Свести проверку `stopping` и публикацию `c.client` в одну критическую секцию под `c.mu`: после
`NewClient` взять `c.mu`, проверить `stopping` ещё раз и, если он взведён, закрыть клиента прямо
здесь и вернуть `ErrConsumerClosed`.

Сделано волной 1. Проверка `stopping` и публикация `c.client` — одна критическая секция под
`c.mu`. Ранняя проверка `stopping` до `consumerOpts` оставлена, но только как быстрый путь:
гарантию даёт повторная проверка под `c.mu` рядом с публикацией. На взведённом `stopping` `Start`
отменяет `pollCtx`, вызывает `client.CloseAllowingRebalance()`, сбрасывает `started` и возвращает
`ErrConsumerClosed`.

**Критерий приёмки**

- [x] В `Start` между `if c.stopping.Load()` и присваиванием `c.client` нет ни одного вызова:
      обе строки — внутри одной секции `c.mu.Lock()` / `c.mu.Unlock()`
- [x] Ветка «`stopping` взведён после `NewClient`» закрывает клиента (`CloseAllowingRebalance`)
      и возвращает `ErrConsumerClosed` — клиент без владельца не остаётся
- [x] `go test -race ./...` проходит под goleak: осиротевший клиент franz-go оставил бы за собой
      горутины heartbeat, и `TestMain` бы это поймал

**Риски:** сброс `c.started` на этом пути означает, что после отказа `Start` конфигурацию можно
исправить и повторить запуск. Откат правки возвращает утечку клиента с живым heartbeat при
SIGTERM во время старта — самый частый сценарий в Kubernetes.

### RF-CONC-03 · P0 · `Stop` по таймауту закрывает клиента при живом цикле опроса → гонка и паника

**Статус:** 🟢 закрыто волной 1
**Прежний ID:** К3
**Где:** `consumer.go:971-979` (ветка таймаута) и `:997` (`CloseAllowingRebalance`).

**Проблема**

Ветка таймаута сознательно пропускает `stopAllWorkers` — её собственный комментарий гласит:
«Карта воркеров не защищена мьютексом и принадлежит циклу опроса: пока цикл жив, трогать её
нельзя». Но 18 строк спустя **безусловно** вызывается `client.CloseAllowingRebalance()`,
который:

1. дёргает `AllowRebalance()` — снимает блокировку, удерживаемую **другой** горутиной;
2. запускает `onPartitionsRevoked` из горутины franz-go, а тот делает именно запрещённое:
   `c.workers[key]` (`:884`), `delete` (`:916`), `close(w.records)` (`:138`).

Одновременно живой `runPollLoop` читает и пишет ту же карту в `worker()` (`:486`, `:496`) и шлёт
в те же каналы в `dispatch` (`:471`).

**Воспроизведено субагентом под `-race`:** `WARNING: DATA RACE` — `closechan` из
`onPartitionsRevoked`/`stopWorkers` против `mapaccess1` в `worker` (`:486`) из `runPollLoop`, плюс
`panic: send on closed channel` в `dispatch` (`:471`).

**Отрицательный результат волны 2:** повторить гонку на исправленном коде не удалось. Пробу будили
на 460/490/505/530/560/600 мс при `-count=4` и на 510 мс при `-count=8` — ни одного `DATA RACE`.
Это ожидаемо после правки (ветка таймаута больше не закрывает клиента), но означает, что
регрессионного теста на саму гонку у нас нет: закреплено только наблюдаемое следствие правки —
`ErrPollLoopStuck` и то, что клиент остался открыт
(`TestStopReportsStuckPollLoopAndLeavesClientOpen`, [06-tests.md](06-tests.md) RF-TEST-09). Верните
безусловный `CloseAllowingRebalance` — этот тест упадёт, но по `Ping`, а не по детектору гонок.

**Чем грозит.** `runPollLoop` — **единственная горутина пакета без `recover`**. Паника уносит
процесс целиком, в момент штатного graceful shutdown. Практический триггер попадания в ветку
таймаута: медленный пользовательский OTel-экспортёр в `c.metrics.workersActive.Add` (`:498`) или
медленный `slog.Handler` в `reportFetchError` (`:452-456`) — оба вызываются прямо из цикла опроса.

*Проверено вручную: `Stop` `:946-1000` прочитан целиком; ветка таймаута действительно не
препятствует `CloseAllowingRebalance` на `:997`; `runPollLoop` имеет ровно один defer —
`close(c.loopDone)`.*

**Решение**

Нужны все три:

1. не закрывать клиента, пока цикл опроса жив, — дождаться `c.loopDone` с отдельным жёстким
   бюджетом после `lifeCancel()`;
2. `c.workers` под мьютекс (`:486, 496, 884, 899, 915, 916`) — инвариант «карта принадлежит циклу
   опроса» ложен уже сегодня, потому что `onPartitionsRevoked` вызывается из горутины franz-go;
3. `recover` + `panicSitePollLoop` в `runPollLoop` — как страховка, а не как лечение.

Сделано волной 1, все три пункта. `shutdown` ждёт цикл опроса через `awaitPollLoop`: мягкая фаза
по `GracefulTimeout`, затем `lifeCancel()` и жёсткий бюджет по `RebalanceTimeout`. При
невышедшем цикле клиент **намеренно НЕ закрывается**, а `Stop` возвращает `ErrPollLoopStuck` —
утечка одного клиента дешевле падения процесса. Карту воркеров защищает `c.workersMu`.
`runPollLoop` несёт `recover` с `panicSitePollLoop`, и порядок defer'ов обратен порядку
исполнения: сначала перехват паники, потом `close(c.loopDone)` — иначе `Stop` пошёл бы закрывать
клиента, пока паника ещё разматывается.

**Критерий приёмки**

- [x] `TestStopReportsStuckPollLoopAndLeavesClientOpen`: при цикле опроса, зависшем в чужом коде,
      `Stop` возвращает `ErrPollLoopStuck`, а клиент остаётся открытым — проверяется `Ping`.
      Это наблюдаемое следствие правки, а не сама гонка: регрессионного теста на гонку нет
      (см. отрицательный результат волны 2), и при откате правки этот тест упадёт по `Ping`,
      а не по детектору гонок
- [x] Все обращения к `c.workers` — под `c.workersMu` (`consumer.go:696`, `:1185`, `:1207`)
- [x] `runPollLoop` содержит `recover` с `c.panics.report(..., panicSitePollLoop, ...)`,
      зарегистрированный ПОСЛЕ `defer close(c.loopDone)` — то есть исполняемый раньше него
- [x] `TestShutdownUnblocksDispatchStuckOnFullQueue`: `dispatch`, упёршийся в полную очередь,
      видит жёсткую отмену, и `Stop` доводит остановку до конца, а не возвращает
      `ErrPollLoopStuck`

**Риски:** `ErrPollLoopStuck` — новый наблюдаемый исход `Stop`, его обязан обрабатывать
вызывающий (это осознанная утечка клиента, а не ошибка коммита). Смены конфига не требует, но
делает реальный бюджет `Stop` длиннее — см. RF-CONC-05.

### RF-CONC-04 · P1 · `awaitWorkers` по таймауту отменяет воркера, но не ждёт его

**Статус:** 🟢 закрыто волной 1
**Прежний ID:** С1
**Где:** `consumer.go:913-927`.

**Проблема**

При исчерпании бюджета код пишет Warn, вызывает `w.cancel()` и **сразу идёт дальше**, не дожидаясь
`<-w.done`. Воркер продолжает выполняться параллельно с закрытием клиента и с финальным коммитом.
Последствие для оффсетов разобрано в [02-kafka-semantics.md](02-kafka-semantics.md) RF-KAFKA-04.

**Решение**

После `w.cancel()` всё же дождаться `<-w.done` с отдельным жёстким дедлайном.

Сделано волной 1: `awaitWorkers` после жёсткой отмены дожидается оставшихся воркеров — **одним
общим бюджетом на всех**, а не по одному на каждого, потому что по отдельности худший случай
умножался бы на число воркеров. Отмена рассылается сразу по всем оставшимся, и лишь потом идёт
ожидание в общем `hardCtx` по `RebalanceTimeout`. Воркер, не вышедший и за этот бюджет,
логируется на уровне Error («Partition worker is still running after hard cancellation»), а не
молча пропускается.

**Критерий приёмки**

- [x] `TestStopAbandonsHandlerIgnoringCancellation`: обработчик, не смотрящий на `ctx`, держит
      сообщение, `Stop` укладывается в бюджет (`GracefulTimeout=200ms`,
      `RebalanceTimeout=300ms`), и брошенное сообщение приезжает заново — проверяется по
      внешнему эффекту через `consDrainFresh`, а не по внутреннему флагу
- [x] В `awaitWorkers` рассылка `kw.worker.cancel()` и ожидание `waitClosed(hardCtx,
      kw.worker.done)` — два разных цикла по `pending`, а не один общий бюджет на воркера
- [x] Невышедший воркер даёт запись уровня Error, а не Warn с молчаливым продолжением

**Риски:** удлиняет худший `Stop` на один `RebalanceTimeout` — учтено в godoc `Stop`
(см. RF-CONC-05). Откат возвращает брошенного воркера, отмечающего оффсет уже отданной партиции
([02-kafka-semantics.md](02-kafka-semantics.md) RF-KAFKA-04).

### RF-CONC-05 · P2 · Реальный худший бюджет `Stop` — `GracefulTimeout + 3×RebalanceTimeout`

**Статус:** 🟢 закрыто волной 1
**Прежний ID:** У1
**Где:** godoc `Stop` (`consumer.go:930-945`), `:966`, `:986-988`, `:997`.

**Проблема**

Godoc обещает `GracefulTimeout`. Фактически к нему добавляются: бюджет `awaitWorkers`, отдельный
бюджет финального коммита (`RebalanceTimeout`) и время внутри `CloseAllowingRebalance`. На
умолчаниях это ≈6 минут против обещанных 3.

**Чем грозит.** Ловушка при выборе `terminationGracePeriodSeconds`: под получает SIGKILL посреди
финального коммита — ровно то, ради чего graceful shutdown и делался.

**Решение**

Привести godoc к коду либо ввести общий бюджет на всю остановку.

Сделано волной 1 по первому варианту: godoc `Stop` называет реальный худший бюджет и советует
заложить его в `terminationGracePeriodSeconds`. Формулировка в коде: мягкая фаза (цикл опроса +
дренаж воркеров) укладывается в `Config.GracefulTimeout`, сверх него в худшем случае добавляются
жёсткая добивка цикла, жёсткая добивка воркеров и финальный коммит — по
`Consumer.RebalanceTimeout` каждая, — плюс время внутри `CloseAllowingRebalance`.

**Критерий приёмки**

- [x] Godoc `Stop` в `consumer.go` содержит раздел «Бюджет» и перечисляет все три надбавки по
      `Consumer.RebalanceTimeout` плюс время внутри `CloseAllowingRebalance`
- [x] Godoc называет `terminationGracePeriodSeconds` — читатель получает готовый вывод для
      деплоя, а не только числа
- [x] Перечисленные в godoc фазы совпадают с кодом `shutdown`: `awaitPollLoop`,
      `stopAllWorkers`, `commitCtx`, `CloseAllowingRebalance`

**Риски:** правка документационная, поведение не меняет. Требует пересмотра
`terminationGracePeriodSeconds` в манифестах у тех, кто выставлял его по прежнему обещанию
godoc, — иначе SIGKILL посреди финального коммита остаётся.

### RF-CONC-06 · P3 · Метрики продюсера пишутся уже отменённым контекстом

**Статус:** 🟢 закрыто волной 1
**Прежний ID:** М1
**Где:** `producer.go:182-196` (defer с метриками) против `:211-212`
(`ctx, cancel := context.WithTimeout(ctx, …)` + `defer cancel()`).

**Проблема**

`ctx` на `:211` — присваивание параметру, не новая переменная, поэтому замыкание видит
timeout-контекст. Defer'ы выполняются LIFO: `cancel()` отрабатывает раньше блока метрик, и
`Add`/`Record` получают отменённый контекст.

**Чем грозит.** Немного: синхронные инструменты OTel не проверяют `ctx.Err()`. Но exemplar'ы и
любой будущий провайдер, уважающий контекст, потеряют данные.

*Проверено вручную: порядок defer'ов и семантика `:=` подтверждаются.*

**Решение**

Контекст таймаута переименован в `sendCtx`, метрики пишутся пользовательским `ctx`. Причина
зафиксирована комментарием прямо над блоком метрик: этот defer зарегистрирован раньше, чем
`defer cancel()`, поэтому исполняется позже него, и `sendCtx` к этому моменту гарантированно
отменён — экспортёр, уважающий контекст, выбросил бы такую запись целиком.

**Критерий приёмки**

- [x] В `SendMessage` объявление таймаута — `sendCtx, cancel := context.WithTimeout(ctx, …)`,
      то есть новая переменная, а не переприсваивание параметра
- [x] В `ProduceSync` уходит `sendCtx`, а `p.sent`/`p.failed`/`p.duration` получают
      пользовательский `ctx`
- [x] `TestProducerMetricsOnSuccess`, `TestProducerMetricsOnFailure`,
      `TestProducerMetricsOnDeliveryTimeout` — метрики пишутся на всех трёх исходах

**Риски:** ни миграции, ни смены конфига. Откат вернул бы отменённый контекст в инструменты OTel:
на синхронных инструментах незаметно, на exemplar'ах и на любом уважающем контекст провайдере —
потеря данных.

## Что осознанно не делаем

- **Ждать каждого невышедшего воркера отдельным бюджетом** — по отдельности худший случай
  умножался бы на число воркеров; после жёсткой отмены ожидание идёт одним общим бюджетом на всех
  (RF-CONC-04).
- **Вводить общий бюджет на всю остановку** — из двух вариантов находки выбран другой: godoc
  `Stop` приведён к коду и называет реальный худший бюджет (RF-CONC-05).
- **Закрывать клиента, когда цикл опроса не вышел** — утечка одного клиента дешевле падения
  процесса; вместо этого `Stop` возвращает `ErrPollLoopStuck` (RF-CONC-03).
- **Обычный `Close` вместо `CloseAllowingRebalance`** — при `BlockRebalanceOnPoll` он повисает,
  потому что уход из группы вызывает ребаланс, заблокированный незавершённым опросом.
- **Считать `recover` в `runPollLoop` лечением** — он оставлен как страховка; лечение — это то,
  что цикл опроса больше не гоняется с закрытием клиента.

## Проверено и признано верным

* Архитектура «горутина на партицию + `BlockRebalanceOnPoll`» корректна; порядок внутри партиции
  сохраняется, разные партиции идут параллельно.
* `dispatch` блокирующий, без таймаута (`:472-477`) — батч не может быть выброшен из-за
  переполнения очереди и «перепрыгнут» коммитом следующего.
* `stopOnce` защищает от двойного `close(w.records)`.
* `Stop` идемпотентен по `CompareAndSwap` (при том что это же свойство усугубляет RF-CONC-02).
* Отдельный бюджет на финальный коммит вместо остатка от `ctx` — верное решение, обосновано
  комментарием.
* Продюсер: `acquire()`/`inflight` (`producer.go:233-244`) корректно закрывают гонку
  «отправка против `Close`»; `TestProducerCloseRaceWithSends` валит себя, если гонка не
  воспроизвелась.
* `go test -race -count=5` и `-race -cpu=1,4` — ноль флаков. Все находки выше лежат вне путей,
  которые эти тесты проходят.
